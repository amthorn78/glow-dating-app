## What P06.2 delivers

PF01's P06 objective is useful communication with enforceable dating-safety boundaries; its development list is the chat adapter and UI, server-mediated send authorization, controlled membership, unread, pagination and reconnect states, idempotent message submission and the token lifecycle. Notification preferences, push and deduplication are P06.3's.

P06.2 delivers it at the scope PF01 allows before P11: a domain and persistence design proven on a disposable PostgreSQL, a provider adapter proven against the development Stream application, and a mobile chat interface on fixtures. **No app runtime gains a database, real authentication or a live provider.** The API keeps its dummy database backend and refuses every connection name; P11 wires persistence, allauth and the production Stream application.

1. **The send and revocation path in the app** (DB06's app half, carried from P06.DB). The reference design's send authorization and revocations (P06.DB D5: `READ COMMITTED`, row locks in one canonical order, the checks after the locks, authorize then deduplicate) become an app persistence adapter behind a domain port, in `services/api`. P06.DB's race suite, through its one interface (P06.DB D1), runs against that adapter in the "Database proof checks" job, with its forced cases, stress run, oracle and negative controls. "Carried into the app" becomes a check, not a claim.
2. **Channel membership and delivery through the outbox.** A match's creation, a send authorization and each revocation write an `OutboxEvent` in the same transaction. Delivery logic turns each event into one provider call: create the match's channel with exactly its two members, send an authorized message on the member's behalf, remove members. The provider's receipt is recorded (`MessageSubmission.provider_message_ref`, `ChatBinding.channel_ref`).
   - **Idempotent by construction** (DM-13 9.4). The channel ID and the Stream user IDs are generated and committed with the event, before the provider call, so a retry reuses them.
   - **No deployed worker before P11** (DM-13 item 9). Stage A runs the delivery logic in-process under the proof's settings, and Stage B runs it from the conformance run. "Delivery" here is code with tests, not a deployed component.
3. **The Stream adapter, behind a provider port, with a fixture adapter.** Channel creation in `glow-match`, server-side send, member removal, user deactivation and per-user token revocation, with random, opaque Stream user, channel and message IDs (ADR 0003; the architecture document, section 8).
   - **How it calls Stream** (DM-13 9.1): Stream's Python server SDK, `getstream`, pinned at 6.1.0 (the version P06.1's harness proved) by hash in the API's lock. It is a significant new dependency in `services/api`, so the Dev Manager reads it with Stage B2's prompt. Stage A adds no dependency: its fixture adapter needs none.
   - **Nothing but IDs and members** (DM-13 9.4, the architecture document's section 8 question on naming). The server sets no `name`, `image` or other custom field on a channel, a member or a user: only the random channel ID and the two members.
   - No invite, call, feed or activity is ever created (its sections 3 and 6). Every provider error maps to a Glow error code; no provider text reaches a user.
4. **The token rules.** A Stream user token is issued only for a valid, current session of an `active` account. It is refused after suspension or deletion, because a token issued after a per-user revocation works (the architecture document, section 8). After a block, the user keeps its token for its other matches; removal from the blocked match's channel ends its reads there (D6).
   - **Lifetime** (DM-13 5.1): one hour. The client discards its token on sign-out. Before P11 the rules are a domain function with tests; P11 serves the endpoint.
5. **The mobile chat interface under the display rule.** The conversation list, a conversation and its composer, with unread, pagination, reconnect, retry and the revoked state, built on the mobile app's fixture adapters, as P05's matches screens are (`apps/mobile/src/interactions/fixture-adapter.ts`), with the shared contracts as the boundary. A test proves that the interface renders only Glow API data: no Stream user or member field, `member.updated`, `ai_indicator.*` or provider error text.
   - **The client half, proven** (DM-13 7.2, option (a)). The mobile app takes Stream's client SDK behind a mobile chat adapter whose only output is Glow's view model: message ID, text, timestamp, own or other, delivery state. An offline test feeds the adapter the SDK's own event objects (`member.updated` with custom data, `ai_indicator.*`, a channel update carrying a name or image, membership changes, `pinned` and `archived`) and shows that none reaches the view model or the render. The new mobile dependency goes to the Dev Manager with Stage C's prompt.
   - **Unread** (DM-13 9.3): a read cursor Glow keeps on the server, per member and match. Every message is sent by Glow's server, so Glow's own accepted `MessageSubmission` rows count what is unread; no grant beyond `read-channel` is needed, and Stream's read state is not used. The cursor's model is in migration `0003` (D7).
6. **The first live step** (P06.1's carried item 1; DM-07 item 4 (a)). The harness's `products.verify` comparison runs before any other live command. Its result closes ADR 0003's condition (c) and the architecture document's section 5 caveat, or stops P06.2 if it differs.

- **D4. The session-expiry rule (CX2, carried item 5).** Keep P06.DB 5.2: the expiry check at a time read after the locks. Narrow O5 to match, keep its detection of the `transaction_start_time` control, and force the boundary with a delay between the check and the commit. **Confirmed by DM-13** (item 3). Enforcing expiry at commit was considered and not chosen: it would need a deferred constraint trigger the suite has never tested, for no safety gain.
- **D5. The send's checks beyond P06.DB's** (P06.DB 5.6). A paused or restricted profile and a withdrawn consent refuse a send. F06 says an unknown pause or contact policy denies contact, and A05 has not set a softer rule. P07 may relax it with Nathan's policy, which then needs its own test.
  - **The consent** (DM-13 4.1): the onboarding consent, the one consent the production contracts define (F02's `ConsentIntent`), held as `ConsentDecision` rows; a send needs the latest decision `accepted` for both accounts. Stage A records the `purpose` value it uses in the data model.
  - **4.1 Each writer joins the lock protocol** (DM-13). The pause, the profile restriction and the consent withdrawal each take the account row lock in the canonical order (P06.DB 5.3) and bump the version of the row the send checks (the profile's or the consent decision's), and the send reads that state under its account locks. Each has forced race cases both ways, as sign-out has (P06.DB 5.1). A writer that cannot join is excluded by name from DB06's claim, with the reason.
- **D6. Revocation and history** (OD-12: after an unmatch or block neither person can send or see the conversation; history kept out of sight only for safety reports). An unmatch or a block removes **both** members from the channel through the outbox. Removal is the mechanism I2b showed meeting the history policy: reads, the open subscription and token reuse all end, and history is kept at the provider. Suspension or deletion deactivates the Stream user, and the token endpoint refuses the account. A channel ban, hide or freeze is never used as a revocation. A message the provider accepted before the revocation committed stays in the kept history; the app neither shows nor re-sends it. 
  - **5.1 Per-user revocation on every session-epoch bump** (DM-13). Suspension and deletion bump the epoch today, and P11's "sign out everywhere" and password reset will too; each revokes the user's Stream tokens per user. Unmatch and block do not, because removal suffices and a per-user revocation would also cut the user's other matches.
  - **The token's lifetime is one hour** (item 4). A single-device sign-out bumps no epoch, so that device's token lives until it expires: reads of channels the user still belongs to, for at most an hour. That residual is a limit, recorded beside DB09.
  - **TD-expiry is closed** by removal and deactivation, which end the open WebSocket on unmatch, block, suspension and deletion (the architecture document's section 8 left it to P06.2). Only the single-device sign-out case remains, bounded by the lifetime.
- **D7. Opaque provider identities need storage.** The models have no mapping from an account to its Stream user ID. Stage A adds one, a new model with a reviewed, unapplied migration `0003`, as P02 wrote `0001` and `0002`. Applying migrations stays P11's. The Stream user ID is random (`secrets.token_hex`), never derived from an account ID, name or email, and never shown or logged. The same migration holds the read cursor (item 5, unread).
  - **The checks** (DM-13 item 6): `makemigrations --check --dry-run` passes in the API's static check and in the proof; `0001` and `0002` are unchanged; the proof's run applies `0003` from zero.
- **D8. What the client reads.** The design under proof stands: the client holds a Stream user token with `read-channel` on its own matches' channels, and renders through Glow's own components only Glow API data plus message text and timestamps. **Considered and not recommended for P06.2:** no client token at all, with Glow's API serving history and realtime itself. It would close S15, the existence oracles, the Video and Feeds exposure and the open WebSocket after expiry by construction. But it needs Glow's own realtime transport, changes the design ADR 0003 accepted, and is Nathan's to decide. 
  - **DM-13 (item 7) did not refer it to Nathan:** the alternative would undo ADR 0003, reopen the provider choice and bring realtime infrastructure forward, for closures the evidence already gives.
  - **7.1 The triggers that send D8 to Nathan** (DM-13), recorded here and in ADR 0003's "Revisit when". If any comes true, D8 goes to Nathan in OD-32's form before the next stage:
    - the mobile client cannot be kept from holding or rendering SDK state beyond Glow's own view model;

    - unread or read state needs a grant beyond `read-channel`.
  - **7.2** is applied in item 5: Stage C proves the client half.
- **D9. Video and Feeds stay closed by construction.** The production plan carries the architecture document's section 5. ## Carried to Stage B and P11 (Stage A's exact-head review and Codex's review, 6 October 2026)

The dispositions are in the evidence record, "Exact-head review of Stage A" and "Codex's review of PR29". DM-14 approved items 1 to 3 with the conditions written here ([report](../continuity/dev-manager/reviews/2026-10-06-dm-14-p06-2-stage-a-governing-read.md)); items 4 and 5, and CX6 in item 2, are Codex's; the Dev Manager reads them, with the stage split and B1's design points below, in DM-15.

1. **F1, the token revocation's cut-off** (DM-14 item 3; B1, with points 2 and 3's provider half in B2). The cut-off is the epoch bump's time read before its commit. The grant's transaction is the persistence adapter's, the signer is B2's adapter. Stage B requires:
   1. the grant in one transaction: the account row `FOR SHARE`, then the session row `FOR SHARE`, in the send's order, with every check of `grant_chat_token` on those locked rows;
   2. the token's issue time is `clock_timestamp()` read under those locks and passed as `now`; the signer sets the JWT's `iat` from it, never from the SDK's clock;
   3. the cut-off is rounded up to the next whole second when sent to Stream;
   4. the cut-off itself stays the bump's pre-commit time, read after the account lock;
   5. tests: a grant forced to wait on a bump refuses after it; a grant that commits just before a bump has an `iat` before the cut-off; each with the app clock skewed ahead. Stage B's conformance run shows that Stream compares `iat` with the revocation time at whole seconds.
   6. **For B2 (DM-15 5.2):** the signer sets `iat` to the issue time **truncated** to the whole second, never rounded to the nearest second or up. "The next whole second" in point 3 is strictly greater: a cut-off of exactly 10.000000 s is sent as 11; B1 tests a cut-off with zero microseconds. B2's prompt states the truncation, and its conformance run shows it.
2. **F3, dead letters** (DM-14 item 4; B1 with the fixture, shown again live in B2). Before the adapter runs live, a dead-lettered `contact_revoked`, `access_revoked` or `session_epoch_bumped` marks its binding (or, for an epoch bump, its chat identity) as needing reconciliation, for example `failed` with the reason; the conformance run shows that state after an injected terminal failure, and its cleanup still removes the run's channels and users. The prompt names P11's reconciliation path; reconciliation itself stays with P11. **CX6** (Codex, P1): a creation whose response is lost leaves the binding `failed` while the channel may exist, and `contact_revoked` then skips removal. A revocation of a `failed` binding still makes the idempotent removal (a channel the provider does not have counts as removed), shown in the conformance run after a creation whose response is lost.
3. **F2, F4 and F5, nits** (DM-14 item 5; B1), listed in B1's prompt, since the grant's change touches `glow_chat/contact.py`: refuse when the locked session's account differs from its pre-lock read in the send, and when the locked match's pair or session's account differs in `unmatch` (F2); an offline test of the deadlock mapping by SQLSTATE (F4); refuse a self-block before the write (F5); each with its test.
4. **CX4, user provisioning** (Codex, P1; the port and the fixture in B1, Stream's call in B2). The port has no operation that creates a provider user: the fixture creates both users inside `create_channel`, and Stream needs both users to exist before a channel names them. Stage B adds an idempotent user provisioning operation to the port (the opaque ID only; no name, image or custom field), delivered before the channel's creation, with the identifiers committed first; the fixture then refuses a channel for an unknown user, so it no longer hides the step.
5. **CX5, match activation's checks** (Codex, P1; B1). `activate_match` checks only the accounts' state, an active block and an existing pair: not reciprocal likes, a paused or restricted profile, or the onboarding consent. It is the proof's and the conformance run's way to make a match, not F09's activation; no runtime path calls it. B1's prompt says so where the adapter is described, and adds under the same account locks the profile and consent checks the send makes. Reciprocal likes and current two-person eligibility are checked under those locks by the activation P11 wires (F09); the data model records the limit.
6. **The next review prompt** (DM-14 item 6) says that fix reversals run in a scratch copy, never the checkout.

**B1's design points (revision 3, with DM-15's conditions as written).** Where the items above leave a choice, B1's prompt sets these, and the session records how it meets each:

- **a. Provisioning before the channel (CX4).** Each `ChatIdentity` that activation creates gets its own outbox event, whose delivery is one idempotent provisioning call. DM-15's conditions:
  - **3.1 A deterministic order key.** Events of one transaction are delivered in the order that transaction wrote them, with neither the app's clock nor a random value deciding. Recommended: a database-assigned, monotonically increasing column on `OutboxEvent` (an identity column), used in place of `created_at, id` after `available_at`; its schema follows point b. Another mechanism is acceptable if the session shows it is equally deterministic and records why. A test writes the channel event and the provisioning events in one transaction and shows the order over repeated runs, not resting on clock values.
  - **3.2 Provisioned only on receipt; no waiting on what lies behind.** The identity gains a state meaning "not yet provisioned", and becomes provisioned only on the provider's receipt. When the channel event reaches the head and either member is not provisioned, it does not retry or wait: it dead-letters with `member_unavailable`, and its binding takes point b's mark.
  - **3.3 Lost provisioning response.** A provisioning event dead-lettered after a call whose response may have been lost marks the identity with point b's mark.
