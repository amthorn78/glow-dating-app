## What P06.2 delivers

PF01's P06 objective is useful communication with enforceable dating-safety boundaries; its development list is the chat adapter and UI, server-mediated send authorization, controlled membership, unread, pagination and reconnect states, idempotent message submission and the token lifecycle. Notification preferences, push and deduplication are P06.3's.

P06.2 delivers it at the scope PF01 allows before P11: a domain and persistence design proven on a disposable PostgreSQL, a provider adapter proven against the development Stream application, and a mobile chat interface on fixtures. **No app runtime gains a database, real authentication or a live provider.** The API keeps its dummy database backend and refuses every connection name; P11 wires persistence, allauth and the production Stream application.

1. **The send and revocation path in the app** (DB06's app half, carried from P06.DB). The reference design's send authorization and revocations (P06.DB D5: `READ COMMITTED`, row locks in one canonical order, the checks after the locks, authorize then deduplicate) become an app persistence adapter behind a domain port, in `services/api`. P06.DB's race suite, through its one interface (P06.DB D1), runs against that adapter in the "Database proof checks" job, with its forced cases, stress run, oracle and negative controls. "Carried into the app" becomes a check, not a claim.
2. **Channel membership and delivery through the outbox.** A match's creation, a send authorization and each revocation write an `OutboxEvent` in the same transaction. A delivery worker turns each event into one provider call: create the match's channel with exactly its two members, send an authorized message on the member's behalf, remove members. The provider's receipt is recorded (`MessageSubmission.provider_message_ref`, `ChatBinding.channel_ref`). Retries are idempotent.
3. **The Stream adapter, behind a provider port, with a fixture adapter.** Channel creation in `glow-match`, server-side send, member removal, user deactivation and per-user token revocation, with random, opaque Stream user, channel and message IDs (ADR 0003; the architecture document, section 8). No invite, call, feed or activity is ever created (its sections 3 and 6). Every provider error maps to a Glow error code; no provider text reaches a user.
4. **The token endpoint's rules.** A Stream user token is issued only for a valid, current session of an `active` account. It is refused after a block, suspension or deletion, because a token issued after a per-user revocation works (the architecture document, section 8).
5. **The mobile chat interface under the display rule.** The conversation list, a conversation and its composer, with unread, pagination, reconnect, retry and the revoked state, built on the mobile app's fixture adapters, as P05's matches screens are (`apps/mobile/src/interactions/fixture-adapter.ts`), with the shared contracts as the boundary. A test proves that the interface renders only Glow API data: no Stream user or member field, `member.updated`, `ai_indicator.*` or provider error text.
6. **The first live step** (P06.1's carried item 1; DM-07 item 4 (a)). The harness's `products.verify` comparison runs before any other live command. Its result closes ADR 0003's condition (c) and the architecture document's section 5 caveat, or stops P06.2 if it differs.

## Design for the Dev Manager's read

- **D1. Stages, each merged before the next starts.** P06.2 is one work item with three implementation stages. Each stage gets its own exact-head review and Codex's review, and merges, before the next stage's prompt is written (OD-08, OD-29). A stage's PR is the manager branch's PR; the next stage opens a new one.
  - **Stage A, server and database (offline; `Glow App - No Stream`).** The domain port and the persistence adapter (items 1 and 2), the fixture provider adapter, the outbox delivery logic against the fixture provider, and the race suite on the adapter. P06.DB's carried items 1, 4, 5 and 6 come first, before the suite's first run on any database (DM-09, DM-12). Items 2 and 3 come with the suite's move onto the adapter. The stage takes no provider call.
  - **Stage B, the Stream adapter, live (`Glow app`).** The first live step (item 6), then the Stream adapter's conformance run against application 1729640: channel creation, send, removal, deactivation and token rules, through the adapter's own code, with the existing guard and cleanup rules of `proofs/stream-chat/`. Before its first live command, the harness takes the C5 review's nits 2 and 3 and its advice to reconsider an allowlist of header names (the P06.1 brief, "Exact-head review of C5"; the handoff's standing item). The prompt authorizes the Stream secret and live actions, so the Dev Manager reads it before Nathan runs it.
  - **Stage C, the mobile interface (offline; `Glow App - No Stream`).** Item 5, on the API's development fixtures, with the display-rule test.
  - Recommendation: the three stages above. **Considered and not recommended:** one session for all of it (too large to review as one head, and it would mix an offline review with a live one); B before A (the live adapter would have no app path to serve).
- **D2. Where the adapter lives, and what stays off.** The domain port in `glow_domain`, the ORM adapter in `glow_persistence` (or a new `glow_chat` module that imports the models; the session chooses and records why), and the Stream adapter beside the existing provider shells. The API's settings, its connection refusal and its dummy backend do not change. The adapter runs only under the proof's settings in the "Database proof checks" job and in a session's disposable database (P06.DB D4). P11 wires it into the runtime.
- **D3. The suite runs twice in the job.** It keeps the reference design as its control and adds the app's adapter as a second subject through the same interface: same cases, races, floors and controls; each subject reported separately. A guarantee holds for the app only when the adapter's run shows it. The reference design stays as the baseline that says the suite can still tell a broken design from a sound one.
- **D4. The session-expiry rule (CX2, carried item 5).** Keep P06.DB 5.2: the expiry check at a time read after the locks. Narrow O5 to match, keep its detection of the `transaction_start_time` control, and force the boundary with a delay between the check and the commit. Recommendation: this rule. **Considered:** enforcing expiry at commit. It is stricter, but PostgreSQL has no check at commit time short of a deferred constraint trigger, which adds a mechanism the suite has never tested. Per the carried item, choosing it would come back to the Dev Manager.
- **D5. The send's checks beyond P06.DB's** (P06.DB 5.6). A paused or restricted profile and a withdrawn consent refuse a send. F06 says an unknown pause or contact policy denies contact, and A05 has not set a softer rule. P07 may relax it with Nathan's policy, which then needs its own test.
- **D6. Revocation and history** (OD-12: after an unmatch or block neither person can send or see the conversation; history kept out of sight only for safety reports). An unmatch or a block removes **both** members from the channel through the outbox. Removal is the mechanism I2b showed meeting the history policy: reads, the open subscription and token reuse all end, and history is kept at the provider. Suspension or deletion deactivates the Stream user, and the token endpoint refuses the account. A channel ban, hide or freeze is never used as a revocation. A message the provider accepted before the revocation committed stays in the kept history; the app neither shows nor re-sends it. **Open for the Dev Manager:** whether the revocation also revokes the user's tokens per user (it ends existing tokens at once, where removal already ends the subscription). Recommendation: yes on suspension and deletion, where the account has no channel left to remove; not on unmatch or block, where removal suffices and a per-user revocation would also cut the user's other matches.
- **D7. Opaque provider identities need storage.** The models have no mapping from an account to its Stream user ID. Stage A adds one, a new model with a reviewed, unapplied migration `0003`, as P02 wrote `0001` and `0002`. Applying migrations stays P11's. The Stream user ID is random (`secrets.token_hex`), never derived from an account ID, name or email, and never shown or logged.
- **D8. What the client reads.** The design under proof stands: the client holds a Stream user token with `read-channel` on its own matches' channels, and renders through Glow's own components only Glow API data plus message text and timestamps. **Considered and not recommended for P06.2:** no client token at all, with Glow's API serving history and realtime itself. It would close S15, the existence oracles, the Video and Feeds exposure and the open WebSocket after expiry by construction. But it needs Glow's own realtime transport, changes the design ADR 0003 accepted, and is Nathan's to decide. The Dev Manager is asked to challenge this recommendation. If it disagrees, the item goes to Nathan in OD-32's form before Stage A starts.
- **D9. Video and Feeds stay closed by construction.** The production plan carries the architecture document's section 5. Whether production also empties `call_member` and the feed-creator grants, or disables Video and Feeds, is P06.1's carried item 3: a question for Nathan before the production application is configured (P09 or P11), not now.
- **D10. The development application stays locked down** (OD-37; P06.1's carried item 4).
