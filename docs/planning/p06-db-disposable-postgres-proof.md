## What P06.DB proves

Against a real PostgreSQL 17 database that exists only inside one CI job (17.11 is the version the 23 September [database audit](database-audit-2026-09-23.md) found on the target service):

1. **Setup, not acceptance.** From an empty database, Django's maintained `auth` and `contenttypes` migrations and the reviewed `glow_persistence` migrations `0001` and `0002` apply, and `makemigrations --check --dry-run` shows that the reviewed migrations still match the models. The proof records the applied ledger. This is setup, not DB01's acceptance (PF01 §6).
2. **Send versus revocation ordering: DB06, partially.** One defined transaction boundary orders a send authorization for a match against every revocation of that contact: a block by either member, an unmatch, a suspension or deletion of either account, and a sign-out or expiry of the sending session. A send authorization is a `MessageSubmission` row for the match's `ChatBinding`, with its `OutboxEvent` in the same transaction; the proof creates the binding locally and calls no provider.
   - After a revocation commits, no send authorization it invalidates commits. The oracle is commit order, not call order (item 6).
   - An authorization that committed first is recorded as such, and the revocation still takes effect.
   - A send carrying a stale contact version is refused.
   - **Retries.** An identical retry (same actor, same idempotency key, same request) by a currently authorized actor returns the first result and never creates a second authorization. The same key with a different request is refused. A retry after a revocation is refused; it never gets the old receipt as if it were current. Two identical requests racing yield one row, and no unique-constraint error reaches the caller.
   - **Unblock does not resurrect.** After a block, an unblock with no new match, then a send with the old or the new contact version: refused (DB06; the P11 plan's rows 90 and 139 to 140).
   - **No deadlock.** Opposing writers, a block by each side and a suspension against a send, show no deadlock and no violation.
   - **Forced and random.** Each interleaving is forced deterministically on two real connections: the send commits first; the revocation commits first; each arrives while the other holds its locks, and the wait is observed in the database (item 6). A randomized stress run then repeats each race within a fixed budget, with zero violations.
   - **Negative controls:** each guarantee has a deliberately broken variant (for example, no row lock, or no version check) that the same suite shows failing, in the same final-head CI run. A race test that has never been seen to fail proves nothing.
3. **Minimal sign-in: DB09, partially.** Maintained Django authentication persistence creates a user and its `AppAccount`. A sign-in records an `AccountSession` bound to the account's `session_epoch`, with a stand-in `auth_session_ref` (D2). Sign-out and an administrative expiry revoke that session; suspension and deletion revoke every session of the account, on every device, through the epoch. A revoked, expired or stale-epoch session cannot authorize a send, including a session that expires while the send waits on a lock.
4. **Evidence and disposal.** The job records the PostgreSQL version (`SELECT version()`) beside the image digest, the applied ledger, every case with its result and its observed waits, the stress run's seed, iterations and overlap count, and each negative control's failure. The database is destroyed with the job. Local runs are iteration, not evidence (D4).

What it does not prove is in D6.

## Design (revision 2: DM-08 applied)

- **D1. Where the proof lives.** An isolated package, `proofs/postgres-ordering/`, like `proofs/stream-chat/`: its own Django settings module, hash-pinned locks and offline tests, used by one CI job.
  - The API's runtime settings, configuration guards and fixture mode do not change. The API still refuses every connection name and keeps its dummy database backend, and no app code path gains a database.
  - The proof imports `glow_persistence`'s models and migrations without changing them. If a reviewed migration fails on real PostgreSQL, the session stops and reports it as a finding; changing migrations is outside P06.DB.
  - The proof's settings never import the API's settings. They refuse to start if `DATABASE_URL`, `HD_API_KEY`, `GEO_API_KEY`, any other name on the API's forbidden connection list, or any `PG*` name is present: libpq reads `PG*` names as defaults, `PGPASSFILE`, `PGSERVICE` and `PGSSLMODE` among them.
  - **No libpq default applies.** The settings give an explicit host (loopback only), port, database name, user and `passfile`, with no service name, so libpq takes nothing from its environment or its default files (`~/.pgpass`, `pg_service.conf`).
  - **A pin test.** The proof's lock pins the same Django as `services/api` (5.2.17), and an offline test fails if the two differ.
  - The send-authorization and revocation functions under proof live in the package as the reference design. P06.2 carries it into the app's persistence adapter; P11A reruns DB06 on the real target.
  - **One interface for the race suite.** The suite drives send, block, unmatch, suspend, delete and sign-out through one small interface, so P06.2 can run the same suite against the app's adapter and "carried into the app" becomes a check, not a claim.
- **D2. Dependencies.** `psycopg` 3 (Django 5.2's supported driver), pinned by hash in the proof's own lock. No allauth: the minimal sign-in uses `django.contrib.auth` and the app's `AccountSession`, and allauth's adoption stays with the item that serves authentication (PF01 §6's rule on bringing integration forward).
  - The data model says `auth_session_ref` is an adapter-provided non-secret library session identifier, and that session metadata alone does not revoke a credential. The proof's random reference is a **stand-in** for that identifier. The reference design is not carried into the app with the stand-in generator: P06.2 or the item that serves authentication supplies the real identifier.
  - So DB09's mark claims only the app-side session revocation ordering against sends, with the epoch's consistency checked but not exercised as the deciding refusal (D6, reworded after DM-09).
- **D3. The CI job.** A new Foundation job, "Database proof checks", runs on every full-scope change like the other application jobs, and the gate requires it. PostgreSQL is started inside the job with `docker run`, not a `services:` container: a service container starts before any step runs, so its password would have to be written into the workflow or held as a repository secret. A password generated in the job, for a database that exists only in the job and reaches no other system, is PF01's "CI-generated credentials" (DM-08).
  1. **Masked before anything can print it.** The step generates the password with `set +x` in force, and its first output is `::add-mask::`. No step runs `docker inspect`, prints the container's environment or echoes the connection options. The password reaches the proof through a file readable only by the job's user (named by the proof's own variable, or as Django's `OPTIONS["passfile"]`), never a `PG*` or `DATABASE_URL` name. It reaches the container by a route that prints nothing, for example the official image's `POSTGRES_PASSWORD_FILE` with the file mounted read-only. It is never stored or set as a repository secret.
  2. **Loopback only, and bounded.** The container is bound with `-p 127.0.0.1:<port>:5432` and has a unique name. The job waits for readiness with `pg_isready` and a fixed limit, and has a `timeout-minutes` like the other jobs. An `if: always()` step removes the container. The job has no `env:` of secrets and uses the workflow's read-only permissions.
  3. **The server settings the proof needs** go on the `docker run` command line and into the evidence: `-c track_commit_timestamp=on` (item 6), and the version from `SELECT version()` beside the image digest. The image is the official `postgres` image at 17.11, pinned by digest.
  4. **The gate** adds the job to its `needs` and to its list of required jobs. On a documentation-only change its output stays "Ordinary documentation: application jobs intentionally skipped". The classifier is unchanged.
  - **A non-superuser role.** The proof connects as a role created in the job that owns the proof's database and is not a superuser, so no case passes because of superuser privileges.
  - The job needs no repository secret (OD-20's CI rule) and reads no inherited connection name.
- **D4. Local runs: within OD-17, not Nathan's** (DM-08). OD-17's constraints are a disposable instance, no connection to a shared or production database, a record of what was tested, and disposal; "in CI" names where the evidence comes from. The manager and the Dev Manager read a disposable instance in the implementation session's own ephemeral sandbox as within it, on four conditions:
  1. **The evidence of record is the CI job's run on the final head only.** A local pass counts for nothing in the record, and the evidence record lists local runs as "iteration, not evidence".
  2. **The same recipe:** a generated password, loopback only, removed afterwards, and none of `DATABASE_URL`, `HD_API_KEY`, `GEO_API_KEY` or any `PG*` name present. It connects to no other database.
  3. **If Docker does not work in the sandbox,** a throwaway PostgreSQL cluster started from a local binary (`initdb` in a temporary directory, listening only on a Unix socket or loopback) is the same thing under the same rules. The session records its version, since it may differ from CI's 17.11. If neither works, the session iterates through CI.
  4. **The report says which was used.**
- **D5. The transaction design: `READ COMMITTED` with row locks** (DM-08). It matches the data model's unit-of-work table (the send's "same revocation lock boundary"), and it is the design P06.2 takes. `SERIALIZABLE` runs, if at all, only as a recorded comparison with its own negative control: it guarantees only when every participating transaction runs at that level, and its retry handling would pass to P06.2.
  - **The send**, in one transaction: lock the lower account, the higher account, the match, then the sending session's `AccountSession` row, each with `SELECT ... FOR UPDATE`; check, under the locks, that the match is `active`, that no `active` block exists in either direction, that both accounts are `active`, that the session is `valid`, unexpired and at its account's current `session_epoch`, and that the contact version equals the one the client sent; then deduplicate (5.4) and insert the `MessageSubmission` and its `OutboxEvent`.
  - **The revocations**, each with the same locks in the same order, as the data model's block, unmatch, suspend and delete row says:
    - a **block** by either member records its `Block` row (inserted, or `removed` to `active`), bumps the blocking account's `blocks_version`, and turns an `active` match `restricted` with its contact version bumped, as the P05.3 domain rules do; an **unblock** removes the block and leaves the match as it is, so contact does not come back;
    - an **unmatch** turns the match `unmatched` and bumps its contact version;
    - a **suspension** or **deletion** locks the account row, changes its state and bumps its `session_epoch`; it does not lock or bump each of the account's matches, because the send checks both accounts' state and the session's epoch under the account locks (5.3);
    - a **sign-out** or an administrative **expiry** locks the session row the send locks and changes its state (5.1).
  - A block that does not exist yet has no row to lock. The account locks, which every writer takes, order a first block against a send, as the P11 plan's DB06 row asks: persistent account rows, not only locks on existing block rows. Each block also bumps the blocking account's `blocks_version`, the persistent account revision; the send does not need to read it, because it holds both account locks. (Corrected after the exact-head review, F5: this said the account locks "and each account's `blocks_version`" order it. The design is unchanged.)
  - **5.1 Sign-out and expiry join the lock protocol.** Otherwise a send that read its session as valid before a sign-out could commit after it: a new authorization after a revocation. A forced interleaving tests it both ways: the send waits holding its locks while sign-out tries, and the reverse.
  - **5.2 Time is read after the locks.** PostgreSQL's `now()` is the transaction's start time, so a send that waited could accept a session that expired while it waited. The expiry check uses `clock_timestamp()` or `statement_timestamp()` after the locks are held, or one time taken after locking. A test covers a session that expires during the wait.
  - **5.3 One canonical lock order for every writer, whoever acts.** A block by the higher account still locks the lower account first. The choice above stands: account-wide revocations lock the account row, not each match. A test runs opposing writers, a block by each side and a suspension against a send, and shows no deadlock and no violation, since PostgreSQL's deadlock detector would otherwise turn a design error into a silent retry.
  - **5.4 Idempotent retries: authorize first, then deduplicate.** Under the locks the actor and session are authorized first, then `(actor, idempotency_key)` is looked up (the P11 plan's row 138: an identical retry by a *currently authorized* actor recovers the original receipt). A retry after a revocation gets a refusal. Two identical requests racing yield one row: the second waits on the locks, then finds the first. A unique-constraint error on `message_dedup` never reaches the caller as a failure. Forced test.
  - **5.5 A locked read that finds no qualifying row is a refusal.** Rows are locked by primary key, and their state is checked in code. A `FOR UPDATE` that also filters on state can return nothing under `READ COMMITTED`, because the row is re-read at its newest version; that means "refused", never "absent, so create". Every value the checks use is read after the locks, inside the same `transaction.atomic()`; no model instance fetched before the lock is reused.
  - **5.6 The send's checks against the data model's "current two-party eligibility".** The match's `restricted` and `unmatched` states and every account state but `active` refuse. A paused or restricted profile and a withdrawn consent are **excluded** from P06.DB: A05 has not set their effect on an existing conversation, so P06.2 or P07 adds them. **Deletion** is the lifecycle transition, not a hard row delete: the account moves to `deletion_pending`, its epoch is bumped, and the `DeletionJob` and `DeletionTombstone` are created as the data model says. `CASCADE` would erase the committed authorization the proof must show was recorded.
- **Item 6. The proof's honesty** (DM-08, conditions 6.1 to 6.3).
  1. **A commit-order oracle.** With `track_commit_timestamp=on`, each row's commit time is `pg_xact_commit_timestamp(xmin)`. The invariant: no `MessageSubmission` commits after a revocation that makes it invalid, whether by a lower contact version, or by its session or an account revoked earlier. Each revocation writes a row in its own transaction (its `OutboxEvent`, or a proof log row), so the oracle reads every revocation's commit time too. The stress run applies the check to every row, not only to what the test code believes happened.
  2. **Each forced wait is observed.** Before releasing the first transaction, the test confirms from `pg_stat_activity` (`wait_event_type = 'Lock'` for the second connection's backend) or `pg_locks` that the second is blocked. The evidence records that each "while it holds the locks" case was observed waiting.
  3. **Negative controls in the same run.** Each broken variant runs in the final-head CI job and is shown failing there, not only locally. A forced case's control fails deterministically. A stress control must fail at least once within its iteration budget, and the evidence records the first failing iteration. The stress run records its seed, iterations and a measured overlap count, so "zero violations" is known not to come from races that never overlapped. Its budget is fixed in code: iterations per race and a wall-clock cap under the job's timeout, so a slow runner cannot make the job flaky (OD-21).
- **D6. What "partially evidenced" claims** (DM-08, item 6). On success the P11 acceptance plan marks DB06 and DB09 "partially evidenced in CI (P06.DB)", worded as follows. Nothing else changes status.
  - **DB06:** on PostgreSQL 17, the reference design orders send authorizations against block, unmatch, suspension, deletion and sign-out, with the guarantees listed, under forced and randomized races.
  - **DB09:** the app-side session revocation ordering against sends (sign-out, expiry, and account-state revocation, which bumps the epoch); the epoch's consistency is checked but not exercised as the deciding refusal (reworded after DM-09); with a stand-in session reference; not maintained authentication, verification, recovery, linking, credential revocation or allauth, which stay with the item that serves authentication and with P11.
  - **What it does not claim:** that the app enforces any of it (the design is in the proof, not the app, until P06.2 carries it and tests it again); DB06's provider half (channel membership, and a send the provider has already accepted), which stays with P06.2 and P11; the P11 target, its roles, pooling or load; maintained authentication. P11A and P11B still rerun DB06 and DB09 on the real target, and DB01, the move-out path and every other deferred case stay with P11. No app route, served feature or provider call changes.
