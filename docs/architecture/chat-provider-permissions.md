## 1. The design under proof

Stream Chat is the chat provider. Glow's design gives a client the least it needs:

1. **The app server controls channel membership.** It creates a match's channel with exactly its two members, in the `glow-match` channel type, and removes a member (or acts on the account) when a match ends. Clients never create channels, join them, invite to them or change their members.
2. **The app server authorizes and sends every message.** A client never sends through Stream directly. It asks Glow's API, which checks the match and block state and sends on the member's behalf with the server SDK (the proof's fixture `AppSendService`: refused sends make no Stream call).
3. **A client's token lets it read its own current match's channel and nothing else.** The `user`, `guest` and `anonymous` roles hold no application-scope grant, every default channel type is closed to every role, and `glow-match` grants members `read-channel` only. Read events stay on; typing events and every content feature are off.
4. **Glow displays only Glow's data** (ADR 0003, the display rule): every name, photo and profile field comes from Glow's API; Stream user and member data, member custom data and `member.updated` events are ignored; provider errors reach users only as Glow's own wording.

What the proof tests is whether Stream's permission model enforces 1 to 3 against a modified client holding a valid user token, and what 4 must cover because configuration cannot.

## 5. The configuration, as a reapplicable plan

The plan is what the harness applies, verifies and can restore against application 1729640, with the target application fixed by `STREAM_APP_ID` (the harness refuses any other). For a production application the same plan runs with that application's credentials, after a `baseline` read and a dry run; the development application's lockdown itself is not a production control.

**Chat** (`configure`, P06.1-I1; `glow_stream_proof/configuration.py`; not a difference: it re-sends the whole target):

1. `PATCH /api/v2/app`: `disable_auth_checks: false`, `disable_permissions_checks: false`, `guest_user_creation_disabled: true`, and empty `grants` for `user`, `guest` and `anonymous` (the `.app` scope is shared by Chat, Video and Feeds).
2. `PUT /api/v2/chat/channeltypes/{name}` for each of `commerce`, `gaming`, `livestream`, `messaging`, `team`: empty grants for every role (features unchanged).
3. `glow-match` (`POST`, then `PUT /api/v2/chat/channeltypes/glow-match`): `channel_member` gets `read-channel` only; every other role nothing; `typing_events`, `connect_events`, `custom_events`, `reactions`, `replies`, `quotes`, `mutes`, `uploads`, `url_enrichment`, `polls`, `shared_locations`, `user_message_reminders`, `delivery_events`, `count_messages`, `mark_messages_pending`, `push_notifications`, `reminders` off; `read_events` and `search` on; `commands` empty; `automod` disabled; `max_message_length` 5000.
4. Required as they are: `permission_version: v2`, and `member_custom_on_typing_events_enabled`, `member_custom_on_messages_enabled`, `member_custom_on_mentioned_users_enabled` false. Every other application setting must keep the recorded baseline's value (no webhook, hook, custom action handler or application-wide token revocation).

The verification (`configuration.verify`) checks all of it before every run, after every run and in every dry run.

**Video and Feeds** (`configure --products video,feeds`, P06.1-I2b; `glow_stream_proof/products.py`; a difference):

5. For every call type (`GET /api/v2/video/calltypes`) where `user`, `guest` or `anonymous` holds a grant: `PUT /api/v2/video/calltypes/{name}` with `grants` naming only those roles with `[]`.
6. For every feed visibility (`GET /api/v2/feeds/feed_visibilities`) likewise: `PUT /api/v2/feeds/feed_visibilities/{name}`.

Stream documents that a grants update changes only the roles named, so `admin` and the resource roles (`call_member`, `feed_member`, …) are untouched. **Why this is narrower than I1's** (DM-05 finding 9 (a)): I1 emptied every role's chat grants, `admin` included (OD-13's side effect: a dashboard tool acting client-side as the dashboard user may be refused). Glow's tokens carry the `user` role, so the Video and Feeds lockdown removes only what `user`, `guest` and `anonymous` tokens can do and spares the dashboard user's Video and Feeds. What a call's member or a feed's owner can do through a resource role is not removed; section 6 records what I2b saw of it.

**What configuration cannot remove.** Three things remain after the lockdown, none of them the `user` role's:

1. **What a call's member or creator keeps** (`call_member`, and the creator's call-level role): read the call, update its custom data, add a member, send a custom event, and by the baseline's grants also join, send audio and video, start and stop recording, transcription and broadcasting. The lockdown does not touch these roles, by design (section 5: narrower than I1's, so the dashboard user's Video and Feeds stay). Closed for Glow by a design constraint: **the server creates no call for a user**, so no member or creator exists; the client roles cannot create one. Emptying `call_member` per call type would remove it by configuration too; that is a decision for Nathan, not made here.
2. **What a feed's creator keeps**: add and edit activities in a feed the server created. Closed the same way: **the server creates no feed and no activity for a user**.
3. **The activities query** (`POST /api/v2/feeds/activities/query` filtered on another user) returns that user's activities with their text and IDs after the lockdown, to a token whose `user` role holds no Feeds grant and whose `.app` scope is empty. Stream does not document which grant governs `QueryActivities`; the proof found no configuration that refuses it. For Glow it is closed only by the same constraint (no activity exists) and by P06.2 never enabling Feeds for users; it is recorded for Nathan's decision whether to ask Stream or to test the remaining roles.

And one signal: the refused calls query (403 code 102) says that "some calls match your query", so a token learns that another user has calls, though not which. With no call created for a user, nothing matches.

## 7. The display rule, S15, deletion and export, and the fallback

- **The display rule** (ADR 0003) is Glow's answer to S15 and to every path in section 3 that configuration does not close: the app renders only Glow API data; it ignores member custom data, the other member's member fields and flags, `member.updated` and `ai_indicator.*` events; provider errors reach users only as Glow's own wording; server and operator consumers never forward Stream member or user custom data. Its limit: it relies on the recipient's app, which the writer cannot change; the residual channel needs two matched people who both run modified apps, and gives them nothing they could not do outside Glow.
- **Member custom data in deletion and export** (B7 (b)): the data lives on the membership of the match channel at Stream; export must read it (`GET /api/v2/chat/members`, or the channel query) before the hard delete removes the channel, and deletion must cover it. P07 and P08 own this.
- **The fallback** (B7 (d)): one channel per person, in which the other member never shares a channel object with the writer, stays the recorded fallback if the display rule cannot be shown to hold in P06.2. A provider-level closure (a `before_message_send_hook_url` cannot see member writes; a webhook clearing member custom data could) stays Nathan's option, not chosen.

## 8. Constraints and open questions for P06.2

The design is P06.2's; nothing here decides it.

- **Revocation.** No Stream mechanism meets the history policy on its own. The unmatch or block path must: remove the member from the channel (ends reads, the subscription and token reuse; the member's own write gets 404), refuse further tokens for a blocked user at Glow's token endpoint (a token issued after a per-user revocation works), and keep the history for safety reports server-side (a hard delete removes it). A channel ban, hide or freeze is not a revocation. Whether the app also revokes tokens per user, and how it handles an open WebSocket that outlives its token (TD-expiry), are P06.2's to decide.
- **Free-text paths.** Member custom data, the other member's membership, `pinned` and `archived`, and `ai_indicator.*` events reach the other client; invites must not exist. The chat UI renders only Glow API data (with a test that proves it); the client SDK's member and AI-indicator state is never read.
- **Existence oracles.** Channel and message IDs must be random and opaque, never derived from Glow's account IDs, names or emails, and never shown to users.
- **Identity.** Stream user IDs are random and opaque (ADR 0003); the user's role is `user`; guests and anonymous users are never created.
- **Video and Feeds.** Glow uses neither product, but every Glow user token reaches both on the same host. The production application must carry section 5's Video and Feeds plan (the client roles at `[]` in every call type and every feed visibility), verified like the chat plan; the harness's scoped `configure` is its executable form. The lockdown removes what the `user`, `guest` and `anonymous` roles grant; it does not touch the resource roles a call's member or a feed's owner holds, so Glow's server must create no call and no feed for a user, and P06.2's design must not add either without its own proof. Run V2 showed what remains if one existed: a call's member reads, updates and adds members to the call and sends custom events to its members; a feed's creator adds and edits activities; and any user token can query another user's activities by `user_id` and read their text, which no configuration in this plan removes (section 6).
- **Open questions** for P06.2: whether Glow reads any member field at all; how channels are named; whether the app revokes tokens per user on block; whether the mobile client can be kept from rendering SDK state it did not ask for.

## 9. What the proof does not show

- A send racing a revocation at the database level (P11's DB06); a real provider outage (only one injected in the process); economics (a dashboard discovery Nathan runs).
- That the app's own mobile client renders nothing it should not: the proof exercises the SDK and the API as a modified client would.
- Push notifications (P06.3) and webhooks: none were configured.
- Real persistence, concurrency or restore (P11); only the development application, its plan and synthetic users at the time of the runs.
- Stream Video and Feeds beyond what a user token can do through their REST endpoints on the chat host: no media session, no call joined, no event over the Video WebSocket, no push, no recording or broadcast. The requests went to the chat host (`chat.stream-io-api.com`), as Stream's server SDK sends them, and were answered there; the Video host (`video.stream-io-api.com`) and the Feeds host were not exercised. The runner holds a chat WebSocket only, so a Video event (`custom`, `call.member_added`, `call.updated`) reaching the other member was not observed; the reads were. What a resource role (`call_member`, `host`, `speaker`; `feed_member`, `feed_follower`, `feed_moderator`) lets a client do when a call or feed exists was seen only through the fixtures the proof created (a call's member reads, updates, adds a member and sends a custom event; a feed's creator adds and edits activities); the proof created no call or feed for a user in Glow's name.
- Timing: the mechanisms' observations used 2.5 s event windows; slower deliveries are not ruled out.
