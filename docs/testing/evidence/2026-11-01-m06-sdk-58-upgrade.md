## 6. The type-only fix (3.4)

- **The cause:** in React Native 0.88's generated types, `View` and `Text` are function components. So `useRef<View>`, `useRef<Text>` and `View | null` are no longer host instance types.
- **The errors:** `npm run typecheck` gave the same 11 errors in the same 3 files as trial (b): `src/chat/screen.tsx:63,109,138` (4 of them implicit `any`s at 109), `src/components/ui.tsx:42,51,64` and `src/interactions/controls.tsx:22`.
- **The fix:** the refs are typed as `HostInstance`, which `react-native` 0.88.1 exports (`types_generated/index.d.ts:167`, `HostInstance = ReactNativeElement`).

Every changed line (commit `bba791f`):

| File | Line | Kind | Change |
| --- | --- | --- | --- |
| `src/chat/screen.tsx` | 4 | import | `type HostInstance,` added to the `react-native` import |
| `src/chat/screen.tsx` | 60 | annotation | `rowRef: (node: View \| null) => void` → `(node: HostInstance \| null) => void` |
| `src/chat/screen.tsx` | 97 | annotation | `useRef<View>(null)` → `useRef<HostInstance>(null)` |
| `src/chat/screen.tsx` | 98 | annotation | `new Map<string, View>()` → `new Map<string, HostInstance>()` |
| `src/chat/screen.tsx` | 115 | annotation | `(node: View \| null) =>` → `(node: HostInstance \| null) =>` |
| `src/components/ui.tsx` | 3 | import | `type HostInstance,` added to the `react-native` import |
| `src/components/ui.tsx` | 30 | annotation | `focusText(node: Text \| null)` → `focusText(node: HostInstance \| null)` |
| `src/components/ui.tsx` | 46 | annotation | `useRef<Text>(null)` → `useRef<HostInstance>(null)` |
| `src/components/ui.tsx` | 55 | annotation | `useRef<Text>(null)` → `useRef<HostInstance>(null)` |

  - only after a macrotask: `screen-birth` 1 attached and 0 visible; `screen-eligibility` 1 visible; `development-link` 2 attached and 1 visible.
- **What the two show:** two mechanism changes in Router 58, as follows.

1. **Navigation lands after the click's task.**
   - The migration guide: "`navigation.dispatch` and navigation helper actions are now queued until after the current React commit".
   - The web stack hides an unfocused screen with `display: 'none'` and keeps it attached (`expo-router/build/react-navigation/native-stack/views/NativeStackView.js:140`).
   - Each failing step follows a `router.push` (`birth-back` → `/eligibility`, `profile-leave` → `/profile`, `open-reset` → `/reset-password`). It then uses a control that **both** screens show (`development-link` and `logout` in the shared onboarding shell; the fixture-outcome panel).
   - The test's `active()` lookup can resolve the outgoing screen's copy before the push lands. That copy is then hidden but still attached, so Playwright keeps retrying it.
   - On Router 57 the push was applied within the click.
   - A scan of all seven spec files found these five sequences, and no other click immediately followed by a shared control after a synchronous push.
2. **A route whose guard fails renders a redirect instead of being removed.**
   - In `onboarding.spec.ts`, a `wrong_context` reset turns the `reset-password` guard false while that screen is shown.
   - Router 57 removed the route, and the stack fell back to `recovery`.
   - Router 58 renders `<Redirect href="/">` there (no `redirectTo`, no anchor), and `index` sends the signed-out member to `/account`.
   - The local page snapshot shows the account screen, with the store's error alert.
   - The reset screen is unreachable on both.

**The stop rule (3.7) is not met:**
- no fix changes what a guard allows;
- none touches app source;
- the source change stays type-only.

A `redirectTo="/recovery"` in `_layout.tsx` could restore 57's landing, but it was not used, for two reasons:
- **an ordering hazard:** on a *successful* reset the guard also turns false, and `reset-password.tsx:20` calls `router.replace('/account')`. The guard's redirect to `/recovery` and that replace would both be queued, in an order the new queue does not fix;
- **it is a design choice:** it would change where a member lands, for a mechanism 3.6 already covers.
