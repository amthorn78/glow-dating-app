## 3. Item 1 — F1: fix it in C2-C3

**The defect is real, and the code shows why.**

- `lastRead` and `cursorKnown` are set together, on a command's success (`:322`), and cleared together, in `resetConversation` (`:190-191`) and `revoke` (`:340-341`). So `cursorKnown` is true exactly when `lastRead` is set.
- When a head read is answered `stale`, `readHead` clears `newerCursor` and queues a read with no cursor. That read's page goes through `mergeHead`'s newest branch, which replaces `accepted` with the newest page.
- `lastRead` can then lie before the window, so `from` is −1. `passesOther` reads only the new page, and `cursorKnown` suppresses DM-25 3.1's fallback (`:315`).
- With the member's own messages filling that page and an incoming message before it, viewing the newest sends nothing.
- **Worse than CX10 on its path:** a later list read cannot heal it either. `cursorKnown` holds the move back whatever the summary says. It clears only when an incoming message comes back into the window: a later one, once viewed, or an older page that brings B back (DM-25 3.2's older-page trigger then finds it).

**Its reach is narrow,** and the record should say so (the AM8-03 lesson).

- C1's server answers `stale_version` to a newer cursor only when the cursor cannot be read, or its match or boundary cannot be placed (`reads.py:389-411`; `chat_projections.py`'s `CursorError`). Normal operation does not produce that: a newer cursor's boundary is an accepted message of the same match.
- The path also needs an incoming message the member has not viewed, followed by a full page of the member's own.
- The fixture never answers `stale`.

**Why (b), by DM-23's rule:**

- **It misses C2's item 8 on its path.** The member has seen newer messages, and the cursor does not move.
- **It is in a correction class the re-review prompt names:** failing to mark read, by DM-25 3.1 to 3.2's rules, a message that has been in view.
- **A unit test shows it offline.** A test transport answers one head read `stale`, as CX9's tests held reads with a wrapper. So it is not a defect "only P11's environment can show", the clause that carried finding 3 and C2C2-X1.
- **It is CX10's own fix leaving a path open.** DM-25 decided CX10 is fixed before the merge, and that covers its paths.
- **The fix is small:** one test in `moveReadCursor`, with its tests.

**The Dev Manager's share.** DM-25 3.1's "Once a command has succeeded, DM-23 2.3 holds as written" assumed that `lastRead` stays in the loaded window. `readHead`'s `stale` branch replaces the window, and I did not trace it. My error, in DM-25.

**Where the proposed conditions fall short:**

- **d.1's test, `cursorKnown && from >= 0`, is right.**
  - `from >= 0` means `lastRead` is among the loaded accepted messages, and `lastRead` is set only while `cursorKnown` is. So the two halves always agree, and the test reduces to `from >= 0`.
  - Keeping `cursorKnown` then leaves a flag whose clears change nothing: wherever it is cleared, `lastRead` is cleared too, and `from` is −1.
- **d.2's "one test per clear of `cursorKnown`" therefore cannot be met.** A reversal that keeps either clear out fails no test. That is the same kind of error as DM-24 1.4's impossible pairings (DM-26 item 1), and it is caught here before a session meets it.
- **d.2 names only the reviewer's sequence, and F1 has two cases after the fix.** The record does not say whether the reviewer's probe held a summary.
  - With no summary held, or one above zero, the view sends the command.
  - With a summary held at 0, the view sends nothing, and the next list read or older page does, as DM-25 3.4 (c) does. The earlier command's own response leaves such a summary whenever the list was read before.
  - Each case needs its own test.
