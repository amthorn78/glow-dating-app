## 11. Item 9 — The threat model, and the stored digests

### 11.1 — A design fix: the stored idempotency digests (B11)

- **The facts:**
  - The contract binds each command's whole intent by a digest stored in `IdempotencyRecord.request_digest`, 64 characters. The data model: "target and complete canonical intent bound by the digest".
  - The record has "No account FK so a queued retry cannot recreate an erased subject", so it outlives the account until it expires.
  - The only digest built so far is the ordering proof's reference: `hashlib.sha256(canonical).hexdigest()`, unkeyed.
- **Why it matters for SV2.** SV2 is the first slice whose commands carry short, sensitive values. Anyone who can read the table can try every value of a short field until a digest matches:
  - an orientation (one of a handful);
  - a "show me" set (a few values);
  - a relationship status;
  - a birth date and time with a known place.

  Each would come back after a withdrawal removed it, and after the account is deleted.
- **The fix needs no new secret.** Django 5.2.17's `salted_hmac(key_salt, value, secret=None, *, algorithm="sha1")` keys a digest with `settings.SECRET_KEY`, which the proof already generates for each run. Its default algorithm is SHA-1, so the condition names SHA-256, whose hex digest fits the 64 characters.
- **Deletion as well:** withdrawal also deletes the records that carried the withdrawn values (B6b). A key held by the server does not protect against someone who has both the key and the table.
