## 3. Item 1 — the departure: approved as written

**The two pairings DM-24 1.4 names cannot be built:**

- **A held send revoked by a send's refusal.** `send()` returns while `sending` is set, and so does `retrySend()`. No second send can be made while the first is held.
- **A held cursor command revoked by a cursor command's refusal.** `moveReadCursor()` returns while `cursorInFlight` equals the epoch, which is DM-23 2.3's and DM-25 3.3's "at most one command in flight".

**What the session did instead, as the code shows.**

- **`:532` (the held send)** runs `for (const through of ['a cursor command\'s refusal', 'a head read\'s refusal'])`.
- **`:544` (the held cursor command)** runs `['a send\'s refusal', 'a head read\'s refusal']`.
- **The other five cases** run both named refusals (`both`).
- **The revocation happens while the request is held.** Each test holds its request in `gate` before it revokes, then releases it and asserts that the snapshot is the same object (`:532` also asserts that no head read follows). That is 1.4's purpose: a response made before the revocation changes nothing.
- **A head read's refusal is a real path to `revoke()`.** It is one of its four callers: the head read, the older page, the cursor command and the send.

**The prompt's departure rule asked for a stop**, and the session recorded the substitution instead. I do not count that against it: no wording of 1.4 could be met here, the substitution changes no rule or behaviour, and stopping would have gained nothing.

**The Dev Manager's share.** DM-24 1.4 named two pairings that the store's own rules, which DM-23 and C2 already set, make impossible. I record it as the role's error.

## 4. Item 2 — C2C2-X1 and C2C2-X2

### C2C2-X1: not a fix-here class; a P11 requirement, not only a limit

**What happens, in the code.**

- After a revocation, a read made later (on a return to the foreground, after an authority change, or on reopening the conversation; DM-24 1.3) starts with `readHead`. `readHead` publishes `loading` when the status is `revoked`.
- `ConversationScreen` shows the revoked notice only for `revoked`. So until Glow answers, the screen shows "Loading messages…" and an empty list. It also shows the composer, with its send button.
- The status was already set this way in C2's code, and C2-C2 kept it, as 1.3 says.

**Why it is not a fix-here class.** The class is a finding that could "let a revoked member see a conversation's history or send in it".

- **No history is shown:** the store holds none after `revoke()`, and every earlier response is invalidated (CX9's fix).
- **No send succeeds:**
  - for an ended match, `send()` refuses before any request, because `contactVersion` is `null` for a match that is not `active` (`authority.ts`);
  - otherwise, Glow refuses the send, since whatever refuses a read refuses a send (point c), and the refusal revokes again.

**Why it is not a missed item of C2's prompt.** Item 3 gives the revoked state on a refusal, and it does. A read made afterwards is DM-24 1.3's kept behaviour ("today's behaviour"). The session followed the condition as written.

**Why it is not like CX9.**

- CX9 let a response made before the revocation override it: stale information beat a refusal already learned.
- X1 is the current read, made after the revocation, whose answer the screen is waiting for. It shows nothing stale.

**But it falls short of what DM-24 1.2 and 1.3 meant together.**

- 1.2 says "the revoked notice is the only state shown". 1.3 says Glow decides later requests.
- The screen leaves the notice and offers a composer before Glow has decided.
- **The Dev Manager's share:** 1.3 kept today's behaviour without looking at what that behaviour shows while the later read is in flight.

**Why carry it.**

- **Only a real transport opens the window,** as finding 3's window was (DM-23 item 2). The fixture answers reads at once.
- **No member is affected before P11,** which changes the client when it connects it.
- **Fixing it now** would add a pass, a re-review and Codex to P06.2's close, for no change in what any member can see or do.

**Conditions:**

- **2.1 X1 goes to the P11 plan's mobile-client entry as a requirement,** with this text:

Today such a read (DM-24 1.3) sets the conversation to `loading`, so the screen shows the composer, with no history, until Glow answers. ### C2C2-X2: a limit, as proposed

- **What happens:** `cursorInFlight` is keyed to the epoch, as C2's and C2-C1's store already keyed it across a change of conversation. So "at most one command in flight" (DM-23 2.3; DM-25 3.3) holds for each epoch.
- **Across a revocation and a later read,** a new command can overlap one made before. The old answer changes nothing (DM-24 1.1).
- **What the server does:** it decides each command itself (point c) and moves a cursor only forward (C1's `_move`). The two commands' order can therefore change nothing beyond the further target.
- **Why not prevent it:** holding the new command until the old one answered would need a follow-up from an invalidated response, which DM-24 1.1 forbids.
- **2.3 X2 is recorded as a limit** beside C2C1-X1 in the P11 plan's mobile-client entry. The entry says it relies on the same forward-only rule P11 keeps (DM-25 3.7).
