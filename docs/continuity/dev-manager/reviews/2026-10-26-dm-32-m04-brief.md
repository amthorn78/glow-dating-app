## 3. Item 1 — M04's brief

### 3.1 The design

**Sound as designed:**
- D1: its own file;
- D2: the triggers, with no PR trigger;
- D4: the ancestor rule, under which a deleted branch loses no commit;
- D5: the keep-list on `main`, full scope to change;
- D6: the lease, which acceptance check 2 tests;
- D7: the fail-closed reads;
- the choice against GitHub's automatic deletion of head branches, which would delete the manager branch at each PR merge.

**D9 is right.**
- Under `!cancelled()`, a failed Change scope still runs the six jobs, and the gate, kept on `always()`, still fails ("Change classification failed").
- A cancelled run's gate also runs and fails. It is never skipped, so it never counts as a success for required checks.
- D9 adds no false pass: the gate passes only on six successes after `full=true`, or six skips after `full=false`.

**Conditions, for the brief and then the prompt:**

| # | Condition | Why |
|---|---|---|
| 1.1 | **D3, the token's reach, stated exactly.** Replace "where that is practical" with these rules: checkout keeps `persist-credentials: false`; only the step that runs the script has `GITHUB_TOKEN` in its environment, for the PR listing and the deletions; the script never prints the token, and never writes it to disk or to git config | Listing PRs needs the token too, so "only the step that deletes" cannot hold as written |
| 1.2 | **The trust limit, in the CI policy.** The `main`-only condition stops an accidental dispatch, but not a branch's own edited copy. A branch that adds or edits a workflow can run it, on push or on dispatch, with the permissions it declares. A merged change to the cleanup workflow or its script acts at its own merge. The protection is the review of workflow changes (`AGENTS.md`) | The text must not claim a boundary that a branch can bypass |
| 1.3 | **D4, a complete PR listing.** The listing reads every page and fails closed on any error. The summary lists the open PRs it read: number, head and base. A selection test feeds it a two-page listing | Deleting an open PR's head branch closes that PR |
| 1.4 | **D4's fresh-branch case, in the CI policy.** Under the rule, a branch whose head is a commit of `main` counts as merged. A session branch pushed at its start commit, before any work, is deleted at the next merge once that commit is in `main`. Its next push re-creates it | Otherwise sessions and managers would read the deletion as a fault |
| 1.5 | **D6 and D8, the summary as the restore record.** Each deletion's row is written as it happens, so a run that fails midway still names every head it deleted. The summary escapes branch names, as data | The summary is the only way to restore a deleted branch |
| 1.6 | **D7's wording.** A concurrency group never cancels a running run, but a newer pending run replaces an older pending one (GitHub's documented behaviour). The CI policy says so | "It never cancels them" is not exact |
| 1.7 | **D8's mode.** The event sets the mode: a push deletes. The dispatch input is a `boolean` passed through `env:`, never through `${{ }}` inside `run:`. On a dispatch, any value but an exact `false` means a dry run | It rules out expression injection, and the run deletes only when a push or an exact `false` asks it to |
