## 3. Item 1 — CX8: correct it before the merge

**The defect is real, and the stage's own tests assert it.**

- `moveReadCursor` targets `this.accepted.at(-1)`, the newest fetched accepted message, after every head read while the conversation is shown and the app is in the foreground.
- `Page` is a plain `ScrollView` that starts at the top, with no scroll to the newest message and no visibility tracking.
- With 20 messages a page, a conversation longer than the screen clears its unread count on open, though the newest messages are below the fold.
- `store.test.ts:141` seeds 25 messages, 13 unread, and asserts that unread is 0 as soon as the conversation opens: the defect, asserted as the behaviour item 8 asks for.
- `rendered/chat.spec.ts:34` uses one message, which always fits the screen, so it cannot see the defect.

**What it is not:** it is not a safety or privacy defect. The other member never sees the cursor (no read receipts), and no revocation is involved. It is a correctness defect in the member's own interface: a member can leave a long conversation with its newest messages unread and the badge cleared.

**Why (b), and why the CX4 to CX7 precedent does not decide it.**

- **CX4 to CX7 could only be shown with P11's environment.** They concern the live harness, the worker and the provider path, and they were carried because no offline pass could settle them.
- **CX8 is a defect in code C2 owns, and C2's own tests can show it offline today.**
- **It misses an item of C2's own prompt.** Item 8 says "when the member has seen newer messages", and the session's record repeats "has seen". P06.2's closing record says the stage is complete. Under (a) it would close with its own interface failing one of its items, and with a test that asserts the failure.
- **The rule I apply,** and which item 3 uses too: a defect in a stage's own code that misses an item of that stage's prompt is fixed before the stage merges; a nit that misses no item is a follow-up.

**The cost of (b) is bounded:** one change in `apps/mobile`, one re-review of a small diff, and Codex's review of the new head. M04 waits that long (OD-29).

## 4. Item 2 — C2-C1's scope: approved, with conditions

- **2.1 The rule.** The cursor moves forward only to the newest accepted message that has been inside the conversation's visible area, while the conversation was shown and the app was in the foreground.
  - A page arriving never moves it by itself.
  - The evidence that a message was viewed is the rendered layout: either visibility tracking on the message list, or the measured scroll position after scrolling to the message. It is never the fact that a fetch returned.
- **2.2 Opening and new messages.**
  - The screen may open at the newest message by scrolling to it. If it does, the cursor moves only once the scroll has placed that message in view (a measured position or a visibility callback), not when the scroll is requested.
  - A message that arrives while the member is scrolled away from the newest does not move the screen and is not marked read. It is marked read when it is scrolled into view.
- **2.3 The command.**
  - At most one cursor command is in flight, as today.
  - A command is sent only when the viewed position moves forward past a message from the other member, never on each scroll event.
  - The existing rules hold: never backward, never to an unsent message, never for older pages.
- **2.4 Tests,** each with its reversal in a scratch copy outside the checkout, showing the test fails without the fix:
  - **The store's tests:**
    - a page that arrives in the foreground while the conversation is shown, with nothing reported as viewed, sends no cursor command;
    - reporting a viewed message moves the cursor to it and no further;
    - reporting an older message moves nothing;
    - `store.test.ts:141` is replaced: with 25 messages and 13 unread, only the viewed messages clear.
  - **A rendered test** (hosted CI), with a conversation longer than the viewport:
    - the unread count does not clear until the newest message is in view;
    - with the member scrolled up, a new message from the other member leaves one unread until it is scrolled into view.
- **2.5 Scope.**
  - `apps/mobile` only, using React Native's own list or scroll interfaces.
  - No dependency or contract change: `package.json`, `package-lock.json`, `dependency-inventory.json` and `src/contracts/generated/` unchanged.
