## 4. Item 2 — the token strategy (D2)

**Approved:**
- allauth's `JWTTokenStrategy`, with `HEADLESS_JWT_STATEFUL_VALIDATION_ENABLED = True` (its default is `False`);
- `HEADLESS_JWT_ROTATE_REFRESH_TOKEN = True` (the default);
- `HEADLESS_CLIENTS = ("app",)` and `HEADLESS_ONLY = True`.

In 65.21.1, stateful validation works like this:
- it loads the token's session;
- it checks the session's user through Django's `get_user`, which refuses an inactive user and a stale password hash;
- refresh tokens live in the session (`headless_refresh_tokens`), so they die with it.

The app client's routes are under `app/v1/`, with refresh at `app/v1/tokens/refresh`.

**Two corrections:**

- **2.1 The comparison.** Replace D2's "**Session tokens instead**" bullet with:

  > - **Session tokens instead** (allauth's default strategy) would also meet PF01. With stateful validation, both strategies look up the session on every request, so neither is cheaper. The JWT strategy is chosen because it is the contract's planned mapping: short-lived access tokens, and refresh tokens that rotate and die with their session.

- **2.2 The keys.** Replace D2's "**The signing key**" bullet with:

  > - **The keys.** The signing key (`HEADLESS_JWT_PRIVATE_KEY`, RS256, allauth's default algorithm) is an RSA key of at least 2048 bits, generated for each test process and each CI run, never committed, printed or logged, as P06.DB generates its database password. In CI it is written to a file in the job's protected temporary directory and read from that path, never put in an environment variable: the `::add-mask::` command takes one line, so a multi-line key would leave lines unmasked. The identity settings' `SECRET_KEY` is generated the same way, not the proof's committed placeholder, because allauth encrypts the session key into every token's `sid` with a key derived from `SECRET_KEY`, and Django signs each session's password hash with it. P11 supplies both as secret references. SV1 adds no key to any environment template.

  **Why:** the proof's settings set `SECRET_KEY = "p06-db-proof-placeholder-not-a-secret"`. allauth's `session_key_to_sid` uses AES with `sha256(SECRET_KEY)` as its key, so with a published `SECRET_KEY`, anyone holding a token can read its session key.

## 6. Item 4 — the session reference (D5)

**The recommendation works, with one gap.** In 65.21.1:
- **When the row is made:** `usersessions` connects `on_user_logged_in` to allauth's `user_logged_in` signal. The adapter's `post_login` sends that signal for headless requests too, so every sign-in from any client creates a `UserSession` row.
- **Its key:** a `BigAutoField`, not derived from the session key. The row stores the session key itself in a unique column.
- **Ending it:** `UserSession.end()` deletes the Django session.

So the key is a library-provided, non-secret identifier, as the data model requires.

**The JWT's `sid` is not an identifier (G6).** `session_key_to_sid` encrypts the session key with a fresh random initialization vector for each token, so two tokens of the same session have different `sid` values. And `sid` decrypts to a credential. No amendment toward it is wanted.

**The gap (G2):** Django 5.2.17's `update_session_auth_hash` calls `cycle_key()`, which makes a new key and deletes the old session. allauth calls it on a password change while `ACCOUNT_LOGOUT_ON_PASSWORD_CHANGE` is `False`, its default. After that:
- the device's tokens point at the deleted session;
- headless's `expose_access_token` issues a new token pair only when the user changes, so the device gets none (only `meta.session_token`, the new key);
- the `UserSession` reference no longer matches.

There is one more hazard. `JWTTokenStrategy.get_session_token` prefers an `X-Session-Token` header over the token's own `sid`. An actor class built on it could be steered to another session's reference.

- **4.1** Replace D5's "**Recommended:**" bullet with:

  > - **The reference: `UserSession`'s primary key** (`allauth.usersessions`). In 65.21.1, allauth creates a `UserSession` row for every sign-in, from a client of any kind (its `user_logged_in` receiver), keyed by the session key, with a `BigAutoField` primary key that is not derived from the key; and `UserSession.end()` deletes the Django session. `AccountSession.auth_session_ref` holds that primary key. The actor class takes the session from the validated token's own `sid` (the payload `JWTTokenAuthentication` returns), decrypted with allauth's own function at the pinned release, held in memory only and never logged; never from an `X-Session-Token` header, which allauth's `get_session_token` would prefer. The `sid` itself is not a reference: it is the session key, encrypted with a key derived from `SECRET_KEY` and a new random initialization vector for each token. The session confirms these facts from the installed source.

- **4.2** Add to D5, after it:

  > - **The reference holds only while the session key does.** Django's `update_session_auth_hash` makes a new key (`cycle_key`) when a password changes and the session is kept, and allauth then gives that device no new token pair. So `ACCOUNT_LOGOUT_ON_PASSWORD_CHANGE = True`: a password change ends every session, the current one included, and the member signs in again (D6). No other allauth flow in 65.21.1 changes a signed-in session's key; reauthentication does not.

  **The stop rule stays** for anything the installed release does differently.

## 9. Item 7 — verification and recovery by code (D3)

**Approved as designed:**
- mandatory verification and password reset, both by code;
- `ACCOUNT_PREVENT_ENUMERATION = True`. With mandatory verification, allauth "can avoid creating a new account with the same (unverified) email address, because we are going to send an email anyway";

- Django's hashers and validators, minimum length 10;
- email change verified by code. That needs `ACCOUNT_CHANGE_EMAIL = True`, which defaults to `False`, and reauthentication, which does not cycle the key.

**The defect (G1).** In 65.21.1, with `HEADLESS_ONLY` and no `HEADLESS_FRONTEND_URLS`, `default_get_frontend_url` raises `ImproperlyConfigured`. Two mails build links:
- **"account already exists":** `send_account_already_exists_mail` builds the sign-up and reset links. The by-code process sends it for a sign-up with a taken address (`send_verification_email_to_address`, `signup=True`).

So the brief's settings make those two requests fail with a server error where their counterparts succeed. That is the enumeration the prevention exists to stop. There is also a dating-specific reason to send nothing to an address with no account: a mail from Glow reaches whoever reads that inbox.

**Conditions:**

  > With `HEADLESS_ONLY`, allauth then raises `ImproperlyConfigured` wherever it builds a link (`default_get_frontend_url`, 65.21.1), and two of its mails build one: the unknown-account mail and the account-already-exists mail. And Glow's account adapter replaces `send_account_already_exists_mail` with Glow's own message, with no link. Without both, a sign-up with a taken address and a reset for an unknown address would fail with a server error where their counterparts succeed.

- **7.2** Replace acceptance check 3 with:

  > 3. **Enumeration and wrong-account linking:** a sign-up with a taken address and with a new one, a reset for an unknown address and for a known one, and an email change to an address another account holds and to a free one each answer alike, as allauth's prevention defines it, and none raises.
