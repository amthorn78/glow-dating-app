## 4. Item 2 — One consistent view

**One statement is enough for the selection.** PostgreSQL gives each statement one snapshot at READ COMMITTED, and the statement holds every predicate.

**The page's recheck needs the same.** D7 rechecks each page's entries at read time, and D2 does not say how many statements that takes.
- **Two statements read two moments.** A result can then hold at neither moment.
  - **Example:** a candidate is blocked by the viewer and then pauses; the viewer then unblocks.
  - **Then:** a first statement, before the pause, reads the profile as `visible`, and a second, after the unblock, finds no block.
  - **So** the page shows a paused profile, though the candidate was never both visible and unblocked.
- **So the condition:** the recheck is one statement, or the page's reads run in one REPEATABLE READ transaction.
  - A transaction that only reads cannot fail to serialize in PostgreSQL, so the retries D2's alternative fears do not arise for it.
- **Actions are already right:** they recheck under both account locks, and every writer of a fact the predicate reads takes its owner's account row first (`glow_chat`'s writers; SV2's D9).

**Q1:** in the brief, D2, replace:

> ```
>   - **Page reads:** each batch's candidate selection is one SQL statement, so in PostgreSQL's READ COMMITTED it reads one snapshot.
> ```

with:

> ```
>   - **Page reads:** each batch's candidate selection is one SQL statement, so in PostgreSQL's READ COMMITTED it reads one snapshot. Each page's recheck of its entries (D7) is one statement too, so a page's eligibility is read from one snapshot as well; if the recheck needs more than one statement, the page's reads run in one REPEATABLE READ transaction (DM-60).
