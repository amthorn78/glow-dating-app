## 4. Item 2 — the derived-change rule: approved, with conditions

**Why the rule, not DM-18 3.1's narrower set:**

- DM-18 3.1 exists so that every allowed change is decided before the apply. The rule keeps that:
  - the `scopes` losses are derived from the plan and the before-view, and listed before the apply;
  - a materialization field is tested against values read before the apply.
- The narrower set would stop on effects the plan necessarily makes (AM7-04). That stop teaches nothing and leaves the conformance rows unrun.
- **The cost of each choice:**
  - A stop at item 5.3 comes after the apply's `differences after: []`, so the lock is already in place. The narrower set costs schedule, not safety.
  - The rule's cost is that it admits fields Stream adds. Two limits bound them: equality with the scopes the application already wrote, and the 2.3 test.

**Conditions:**

- **2.1 "Re-created or materialized" is measured, not read off the second.**
  - Immediately before and after each apply command, the session runs `date -u +%Y-%m-%dT%H:%M:%S.%NZ` and records both times.
  - A scope counts as re-created or materialized by the write only if all of these hold:
    - the apply wrote it;
    - its `created_at` in the after-view differs from the before-view's, or the before-view read `0`;
    - the after-view's `created_at` lies between the two recorded times.
  - The products apply sends two `PUT`s, which may fall in different seconds, so "the apply's second" is not exact enough.
  - `created_at` is volatile in the comparison, so the session reads it from the two view files directly.
- **2.2 The comparison set, exactly.**
  - **For a chat apply,** the set is every chat type in the before-view that this apply did not re-create. Not "the six other than the one written": a chat apply re-sends every chat type (B2-C2's eight requests moved every type's `updated_at`), so all seven are written.
  - **For the call types and feed visibilities,** the sets are as named: the four call types written on 27 September (their `created_at` is that apply's time), and the five visibilities.
  - **If any scope in the set lacks the field or holds another value,** the field is not of item 3's kind, and the session stops.
- **2.3 The application body's copy.** A copy is allowed only at that scope's own summary path (`app.body.app.call_types.<name>.<field>` or `app.body.app.channel_configs.<name>.<field>`), holding the same value as the scope's field. Any other copy stops the session: a copy without the scope's field, or a copy with another value.
- **2.4 Identity fields on a materialized scope, pre-approved if they occur.**
  - **Why:** the application body's `call_types` summaries carry `app` and `id` fields (B2-C2's record, its listings). The record does not show what the summaries of `agent` and `audio_call`, which read `created_at` `0`, hold for them. If they move from `0` or absent at materialization, the rule as written stops: an `id` can never equal another scope's, and a move from `0` is a changed value. This is the one materialization effect I can foresee that the rule would stop on, and an identifier enables nothing.
  - **The allowance:** on a scope this apply materialized from `created_at` `0`, a field named `id` or `app`, in the scope's own read or its summary, may move from absent, `0`, `null` or `""` to a value. It is listed, and allowed only if:
    - for `app`, its value equals the one every scope of the kind that the application wrote holds;
    - for `id`, no other scope holds its value.
  - **Limits:** a value that was already non-empty and changes still stops the session. No other field is covered.

**Not widened:** apart from 2.4, a field whose value changes on a materialized scope stops the session, even if the new value equals the comparison set's. A changed value changes what the type does, and no read so far shows one. The prompt's "A field that changes value or disappears is not of this kind" stays.
