## 4. Item 2 — point b: approved, with conditions

**What point b gets right:**

- Glow's accepted rows define the page, and the provider is asked only for the texts of IDs Glow committed.
- So a message Glow did not send never reaches a member: a provider system message, or a write through a feature Stream adds.
- This goes beyond the costing's "read from Stream server-side, paginated", in OD-45's direction: "no feature snuck in" holds at the read by construction, not only through the drift check.
- `member_custom_include` is never passed. Every other field, and every message not asked for, is dropped. That keeps ADR 0003's decisions 1 and 3.

**Where it falls short:** point b also says the provider "supplies only the text". As written, a text Stream changed after Glow sent it would still reach the member. That covers:

- a message edited at the provider, through the dashboard or a provider feature;
- a moderation substitution;
- a deleted message, which Stream returns with its own marker or text;
- a message of a type other than `regular`.

In those cases the provider's wording reaches a member, which ADR 0003's decision 3 forbids.

**The fix needs no new column.** Glow already holds a digest of exactly what it sent: `MessageSubmission.request_digest` is `sha256("{match_id}\n{contact_version}\n{text}")` (`SendCommand.request_digest`). The row holds `contact_version`, and the match ID comes from its binding.

**Conditions:**

- **2.1 Only text Glow sent is shown.**
  - The read shows a provider's text only if the digest of the match ID, the row's `contact_version` and that text equals the row's `request_digest`.
  - A message whose `type` is not `regular`, or that carries a deleted marker, is "unavailable" whatever its text.
  - A mismatch is "unavailable" and counted.
  - **Tests:**
    - a text altered by one character;
    - a deleted message;
    - a `system` or `error` message.

    Each must give "unavailable".
  - If Stream turns out to normalize text (whitespace, Unicode), the live row in P11 shows it (8.2). The read fails closed until then.
- **2.2 The order follows visibility.**
  - **The problem:** a message becomes visible to the other member when the provider accepts it, which can be after a later message is accepted. A retried delivery is enough, and B1's order is by writing, not by acceptance (DM-20's note).
  - **The consequence:** if the page order, the "newer than" cursor and the read cursor follow sending order, a message accepted late sorts behind a position the reader has already passed. Polling would never return it, and it would never count as unread.
  - **What C1 does:** C1 states the order it uses and shows, with a test, that a message accepted after a later one reaches the reader's next poll and counts as unread. Either it keys "newer" on an order that follows acceptance, or it relies on per-channel delivery order. In the second case, the P11 plan's "Per-channel order across retries" becomes a requirement for the history read, without its "or records the case".
  - **If either needs a column,** that is a migration: the session stops and reports it (point b's departure rule).
- **2.3 A read writes nothing.** "Counted for reconciliation" means a count in the read's domain result, for P11's metrics. No row is written by a history read or the list.
- **2.4 A provider error fails the read.** A transport error, a 5xx or a rate limit gives Glow's retryable code. It never gives a page in which every message is "unavailable". "Unavailable" is only for a message the provider answered without, or whose text fails 2.1.
- **2.5 No message text in any log line** from the text read, the history read or the projections, with a log-capture test. Under (b), every member's history now passes through Glow's server.

## 5. Item 3 — point c: approved, with conditions

**Whatever refuses a send refuses a read** is the right default under OD-12 and F06. The read checks before and after the provider call.

**Question 1: is refusing a paused member's read of their own history within F06's rule?**

- **As an interim default, yes.**
  - F06 says "unknown pause/contact policy denies contact".
  - The contracts' notes say "pause denies new discovery/contact until policy resolves".
  - D5 already applies the same default to sends.
- **But the policy itself is Nathan's.**
  - PF01's "Chat and notifications" says to "decide the policy for existing conversation history separately from future contact".
  - A05 lists "existing-history behavior" among Nathan's open policies.
- **It also changes what members see, against the design he chose under.**
  - B1's `grant_token` checks the account, the session and the identity only. Under option (a), a paused member could still read their channels.
  - Under this rule, a conversation also vanishes from the other member's list while one member is paused, restricted or suspended, or has withdrawn consent. That reveals the paused member's state to the other.
- **Why it is not a question now:** nothing is served before P11, and C2 runs on fixtures, so no member is affected.
- **3.1 Record it as interim, and ask before serving.**
  - The brief's point c and D5 record the rule as the interim default under F06.
  - The P11 plan names, as a prerequisite to serving the reads, the A05 question to Nathan in OD-32's form:
    - a member's own pause or restriction;
    - the other member's pause, restriction, suspension or consent withdrawal, with what each reveals;
    - deletion.
  - P07's brief takes the same question if P07 comes first.

**Question 2: are the forced cases enough without an oracle rule?**

- **Yes.** A read writes nothing, so the database's records cannot decide its outcome. An oracle rule would have nothing to judge, and the prompt is right to add one only if the records can decide it.
- **The forced cases must be able to fail.**

**Conditions:**

- **3.2 No lock is held across the provider call.**
  - The first check's transaction ends before the call. The final check runs in a new transaction that takes the same shared locks again.
  - A safety action must never wait on the provider.
  - **Forced cases:**
    - a block that commits during the provider call is not delayed by the read (no wait recorded for the block);
    - a revocation already waiting when the final check takes its locks is serialized: if it commits first, the read is refused; if it waits on the check, the page is returned. Both are observed.
  - The prompt's "in a new statement" reads as "in a new transaction".
- **3.3 A planted control.** In the same run, a read variant whose final check is skipped, or runs before the provider call, must fail the forced case "committed while the read waits". That shows the forced case can fail.
