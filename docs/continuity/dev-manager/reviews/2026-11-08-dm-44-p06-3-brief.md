## 3. Item 1 — the brief as a whole

**Scope:** Outcomes 1 to 5 cover PF01's P06.3 acceptance. Content comes only from Glow's server path, with no birth, compatibility or body field. Preferences and devices are at fixture scope. Real transport waits for P09 and P11. The exclusions keep the runtime sealed: `glow_api` is untouched, so the runtime cannot import the new modules. The acceptance checks and D12's checks are right.

**What needs words:** the brief says devices and settings "follow F12 at fixture scope", but four contract facts make parts of it impossible as written:

- **G1:** `NotificationSettings.device_state` is required and takes only `active` or `revoked`. There is no `none`, so nothing valid can be read for an installation that never registered.
- **G2:** F12 lists `settings` only from `active` to `active`, and forbids "Every unlisted transition". Outcome 3's denied path ("the app saves the setting, registers no device") is a settings change with no active registration, so F12 forbids it.
- **G3:** F12 lists `rotate`, but `DeviceIntent.action` has only `register` and `revoke`.
- **G4:** F12's acceptance binds a registration to its session ("Token rotation owner/session bound; logout revokes registration"), but `DeviceRegistration` has no session field. Outcome 2's "every active registration of the account's session" does not say which session.

Also, the contract has one `device_state` while an account may hold several registrations, and `installation_id` is unique across accounts. So F12's states can only be read per installation.

**Conditions:**

  >   - when a registration ends (revoke, logout, or its installation's transfer to another account) or its token is replaced (rotate), the old token is discarded from the store through the port. It fails if the token appears in any record's message or arguments, in any read, `repr()` or `str()` of the domain's objects and refusals, in any exception's text, or in what the transport fixture recorded; and if the reference appears in any record, read or refusal. Its reversal logs the token in one path;

- **3.3 Redelivery.** Replace Outcome 1's "**no duplicate push:**" bullet with:

  > - **no duplicate push:** the first delivery of a trigger fixes its devices: the recipient's active devices then. A later delivery of the same trigger (a retry, a redelivered event) sends only to a device of that set whose send the transport has not accepted and that is still active, so a device registered after the first delivery gets nothing for that trigger. The ledger's key is the trigger's event id with the installation's `device_id`, so a registration revoked and made again keeps its key. The ledger records a send only when the transport accepts it, and the transport's idempotency key is the ledger's key: a send the transport accepted but the ledger did not record is refused as a repeat on the next delivery, and the ledger then records it. Exactly-once delivery by a real provider is P11B's (PV05);

  >   - if the permission is undetermined, the seam asks once;
