## 3. Item 1 — CX12: fix it in C2-C4

**The defect is real, and the manager's verification holds in the code** (`store.ts` at `85b9844`):

- When `loadOlder` (`:271-291`) gets its page back, it tests only `conversationEpoch` (`:278`).
- When a head read is answered `stale`, `readHead` takes the branch at `:244`: it clears `newerCursor` and sets `headAgain`. Its `finally` then sends the queued read with no cursor (`:249`). The manager cites `:248`, which is the line before.
- That page goes through `mergeHead`'s newest branch (`:255-256`). The branch replaces `accepted`, `unsent`, `olderCursor` and `newerCursor`, and no epoch advances.
- **The held older page then passes `:278`:**
  - it is put in front of the new window (`:281`);
  - it sets `olderCursor` from its own page (`:282`);
  - it can fire DM-25 3.2's older-page trigger on the joined window (`:285`).
- **The path is C2's.** The `stale` branch, the newest branch and `loadOlder`'s merge are all at `cb3a6a6` (`:197`, `:208-209` and `:224-234` there). C2-C3's diff does not touch them.

**Its effect, stated exactly.** Two corrections to the consultation's "history out of order and partly unreachable in the open conversation until it is reopened":

- **The messages stay in order, with a silent gap.** In Codex's example, message 5 shows directly above message 31, and nothing marks the 25 missing between them.
  - "Show earlier messages" disappears (`hasOlder` is false).
  - If the late page brings an older cursor of its own, the button loads history before the late page, and the gap still cannot be reached.
- **It lasts while the conversation stays selected, not until it is reopened.** Leaving and reopening the same conversation keeps the store's window:
  - `closeConversation()` keeps `accepted`;
  - `select()` returns at once for the conversation already selected (`:124`), which is the call the list makes (`screen.tsx:50`) and the match's "Open conversation" makes (`interactions/screen.tsx:75`).
  - **It ends** when another conversation is selected or the account changes, at a revocation, at another `stale` reload, or when the app restarts.
  - This is AM8-03's kind of slip: what clears a stuck state was not traced. It has no effect on the verdict.
- **The reach is as the manager states it, with one addition.** C1 answers `stale_version` to a newer cursor only when the cursor cannot be read or its boundary cannot be placed (`reads.py:389-411`; `CursorError`). The contracts give that code to a read only for its cursor. The fixture never answers it.
  - **The addition:** an older-page request made after the `stale` answer, and before the reload's page is merged, is exposed too. At that moment `olderCursor` still names the old window.
  - No other member's data, no revoked state and no send is affected.

**Why it is fixed here (DM-23's rule):**

- **It is PR33's own code, and on its path it misses two items of C2's prompt:**
  - **Item 5:** "It shows them in the order the page gives … It asks for newer messages with the page's opaque `newer_cursor`, and for older ones with `older_cursor`." The store joins two pages that do not meet. The cursor it keeps belongs to a window it has discarded.
  - **Item 7:** "with unread, older pages, point d's polling, retry and the revoked state". Older pages no longer reach the gap.
- **A unit test shows it offline,** with the CX9 gate and C2-C3's `staleOnce`. **The fix is local** to `store.ts`.
- **Carrying it** would put a known defect in front of P11's first real transport, the first place a `stale` answer can arrive. Nothing P11 builds on this path would make the fix easier then.
- **The case for carrying is real but weaker.** The reach is narrow, and each pass costs a session and a re-review. F1 had the same reach, and DM-27 fixed it. Consistency points the same way.

**What else the reload leaves behind: my audit at `85b9844`.** I traced every piece of state tied to the loaded window across `mergeHead`'s newest branch. Only the outstanding older-page request, and the older-page state it published, are left stale. The rest:

- **`accepted`, `unsent`, `olderCursor` and `newerCursor`:** replaced. `hasOlder` follows `olderCursor` (`:117`).
- **`lastRead`:** DM-27 1.1 reads it against the window at each call.
- **`seen` may fall outside the new window.**
  - `noteSeen` then takes the newest message in view as `seen` (`:150-152`).
  - That is a forward move: a newest page that does not hold `seen` holds only later messages.
  - CX12's join is what breaks it. Viewing the late page's messages would move `seen` backward, to a message before the old `seen`. That does no harm at the server, which moves cursors forward only, but the store's state is wrong. The fix removes it.
- **Not tied to the window, or re-applied against it** (`:239`, `:327`): `visible`, `cursorRetry`, a cursor command in flight, a send and the list read.
- **A head read:** the reload is the only one in flight (`:228`).
- **Two answers that need no change**, since the contracts give `stale_version` to a read only for its cursor:
  - `stale` to a read with no cursor (the store would reload at once, again and again);
  - `stale` to an older cursor while the newer one still reads (the older-page error would repeat on each retry). I found no C1 path that removes an accepted message while the match stays readable.

So, as far as the code shows, the family of defects found on this path (F1, which Codex posted as CX11, and now CX12) ends here. 1.4 asks the session to record its own audit, and 2.2 asks the re-review to check it.

**The Dev Manager's share.** In DM-27 I traced the `stale` reload for the cursor's state only. The re-review search I set there (DM-27 1.4) did the same. Neither looked at the other requests that the reload outlives. 1.4 and 2.2 here close that gap.

**Conditions:**

- **1.1 Replacing the window invalidates every older-page request outstanding at that moment** (replaces e.1).
  - **Where:** at the replacement itself, `mergeHead`'s newest branch, not at the `stale` answer.
    - A request made after the `stale` answer and before the reload's page is merged was asked from the window being discarded.
    - So it is invalidated too.
    - **Where it bites:** otherwise the newest branch runs only on the first read after a reset or a revocation, and while the conversation holds no accepted message (C1 then gives no newer cursor). In both cases `olderCursor` is null, so no older page can be outstanding. 1.1 changes behaviour only on the `stale` path.
  - **An invalidated response, success or failure, changes nothing.**
    - It does not change `accepted`, `unsent`, `olderCursor`, `newerCursor` or `hasOlder`.
    - It shows no older-page error.
    - It starts nothing: no cursor command (DM-25 3.2's older-page trigger does not fire), and no read.
  - **The exception: a refusal that ends access** (`unavailable` or `signed_out`), unless the conversation's epoch has moved on first (a revocation, another conversation or another account; DM-24 1.1). It revokes the conversation, as a refusal of an older page does today (`store.ts:289`).
    - **Why:** after a revocation, a late refusal adds nothing, so DM-24 1.1 drops it. Here the conversation is still open, and the refusal may be Glow's first word that access has ended. Dropping it would leave the history on screen until the next poll is refused.
    - e.1 as written would have dropped it. That contradicts e.4's "the revocation rule … unchanged".
  - **The session chooses the mechanism,** and records why. For example:
    - an older-page epoch advanced by the replacement;
    - or a comparison of the request's captured cursor with `olderCursor` before merging. A cursor is opaque, so that comparison tests identity; it computes no position.
  - **A comparison may merge a page whose cursor is identical to the current `olderCursor`.** The page then continues the new window exactly, so that is not a departure.
- **1.2 "Show earlier messages" stays usable** (replaces e.2).
  - **No invalidated request leaves the older-page state `loading`.**
    - The state is `idle` once the replacement is merged, or at the latest once the invalidated request completes.
    - Which of the two depends on the mechanism. The record says which.
    - As e.1 and e.2 were written, the cursor comparison would have left it `loading` for good: the state comes from the old request, and e.1 forbade its response to change it.
  - **A request made after the replacement** asks with the reload's `older_cursor` and keeps today's behaviour:
    - at most one for the current window at a time;
    - its page merges;
    - its failure shows the error;
    - a refusal that ends access revokes.
- **1.3 Tests** (replaces e.3). Each has its reversal in a scratch copy outside the checkout, showing that the test fails without its part of the fix.
  - **The tools:** C2-C3's `staleOnce` and the CX9 gate compose.
    - A helper the gate lacks goes in `store.test.ts`, or in `testing.ts` (1.5).
    - Examples: a held page answered with a refusal, or held requests released one at a time.
  - **(a) CX12's sequence,** in Codex's numbers or any others that leave a gap between the held page and the reload's page.
    - **The steps:**
      - 25 messages, with the window holding 6–25;
      - the older page, 1–5, held;
      - 25 more messages arrive;
      - one head read is answered `stale`, and the reload shows 31–50;
      - the held page is released.
    - **Expected:**
      - the window is the reload's page alone, with the reload's `olderCursor`;
      - the release starts no request;
      - "Show earlier messages" then reaches 11–30 and 1–10, in order, each message once.
    - **Reversal:** today's code.
  - **(b) The same, with the held page failing** without ending access.
    - **Expected:**
      - the window and its cursor are unchanged;
      - no older-page error is shown;
      - the state is `idle`, at the latest after the failure;
      - "Show earlier messages" reaches the gap.
    - **Reversal:** today's code, which shows the error.
  - **(c) The same, with the held page refused because access has ended.**

    - **Reversal:** 1.1's exception removed.
  - **(d) An older page requested after the `stale` answer and before the reload's page is merged.** The reload is held, and the older page is released after it.
    - **Expected:** as (a).
    - **Reversal:** a mechanism that invalidates only the requests made before the `stale` answer.
