### Item 2 — The stop rule: the class rule, approved with conditions

**I prefer the class rule.** An exact list fails on every new addition, and Stream added one within four hours. The four classes are exactly what the targets lock (classes 2 and 3) or what the merged baseline records (classes 3 and 4). Everything else still stops:

- `glow-match` beyond D1;
- a known scope's non-client grants or existing settings;
- feed groups;
- the application settings;
- a missing type.

The full comparisons around each apply still see every field an apply changes.

**What the classes do not see.** `verify` reports only what the targets name, and some things the class rule should also cover are not differences at all: a new role, a change to a role's `.app` grants other than the client roles', a new feed group, and a new channel type, call type or feed visibility with no grant yet. The conditions:

- **2.1 Every line is listed with its class,** and a line new since B2-C1's record is marked new, as the prompt says.
- **2.2 Section 4 item 3's listing gains the lists.** From V0b, compare the following with B2-C1's record:
  - the role list (17 names);
  - each role's `.app` grant count (`admin` 47, `anonymous` 0, `global_admin` 44, `global_moderator` 39, `global_read_only` 5, `guest` 0, `moderator` 42, `user` 0);
  - the names of the channel types, call types, feed visibilities and feed groups.

  The following stop the session before item 4: a new or missing role, a changed `.app` grant, and a new or missing feed group. A new type or visibility is listed, marked new, and takes its class.
- **2.3 Class 4 is judged, not only counted.** Each added settings section is listed with its value. A section that acts without any client request stops the session before item 4: one that records, transcribes, broadcasts, rings, notifies, or sends to a URL by itself. `lifecycle` (`reusable` or `single_use`) does none of these.
- **2.4 A re-created scope is shown as one.** A class-2 or class-3 scope whose `created_at` differs from B2-C1's record is listed with both stamps (item 8).

- **3.1 The after-apply comparisons stop the session.** Items 5.3 and 6.3 say "Anything else is reported first, before any further command" but not that the session stops. Stopping after the chat apply leaves Video and Feeds as they are now, which is acceptable.
- **3.2 A volatile name is the narrowest possible** (point ii). A name joins `VOLATILE_FIELDS` only if both hold:
  - its V0a and V0b values are read-time values: a time that moved forward, or a counter that grew;
  - it occurs nowhere in either committed baseline or among the fields the targets name. A test shows this.

  `VOLATILE_FIELDS` matches by name at any depth, so a common name (for example `count` or `limit`) would hide configuration everywhere. Such a name stops the session instead.
- **3.3 A list in a different order: pre-approved, narrowly.** `changed_fields` compares a list of objects item by item and a list of scalars as one value (`full_view.py`, `changed_fields`). If Stream returns the same items in a different order between V0a and V0b (the role list is the likely case), that is not configuration drift. If the only difference between V0a and V0b is the order of a list whose items are otherwise identical, the session may:
  - make the comparison key that list's items by `name` (or `id`), offline in `full_view.py`, with a test;
  - re-run `compare-views` on the same files and record it.

  Any other difference stops the session. The owned paths add this one change.
- **3.4 No digest of a non-empty withheld value in the record.** B2-C2's evidence section writes such a value as "withheld, non-empty", "changed" or "unchanged", and an empty one as "empty". The digests stay in the `.work` files, which git ignores. A SHA-256 of a high-entropy credential is not reversible, but a committed record needs no digest to say "changed".
  - B2-C1's record already quotes the digests of four non-empty values: `push_notifications`, `webhook_events` and two booleans.
  - On a development application with Stream's defaults the risk is low. The manager may replace them in place with "non-empty"; that is not required.
- **3.5 Stamps of what this session locks.** V2 and the closing `baseline` record the `created_at` and `updated_at` of every class-2 and class-3 scope. If a scope locked in this session reads grants again at the closing `baseline`, that is the closing count's difference, and the session stops and reports it with the stamps. It would show that a lock does not hold against Stream's own re-creation (item 8).
