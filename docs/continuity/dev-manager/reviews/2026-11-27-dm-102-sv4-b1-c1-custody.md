## 3. Item 1: the custody fix's form

### 3.1 What the code does today

I read it and confirm both findings:
- **Where the reference is parked.** `device()` calls the store's `put` before `_run`, then parks the fresh reference whenever `done is None or not done.saved` (lines 460 and 461).
- **What `done is None` covers.** `_run` answers `done=None` for three different things: a refusal, which rolled back; a deadlock, which rolled back; and any other error, including one at the commit itself, where nobody knows whether it committed.
- **B1R-2, the wrong guess.** An unknown outcome is read as "not saved". If the commit did happen, the reference now sits on an active registration and in `PendingTokenDiscard` at once. The next revoke's `_hold_for_discard` then fails the table's uniqueness, and B2's sweep would discard a token in use.
- **B1R-1, the lost reference.** `_park` catches every failure of its own insert and only logs (lines 370 to 376). With the database unreachable for that statement, the reference is held nowhere.

Both are faults at the custody boundary. Codex found each on its own (comments 4713760650 and 4715163584).

### 3.2 Why (b)

The root of both findings is the same: today the handle on a fresh reference is created *after* the outcome, from a guess about the outcome. (a) improves the guess. (b) removes it: the handle exists before anything can go wrong, and every later path either consumes it or leaves it for the sweep.
- **(a)'s residual is the worse one.** After a lost commit acknowledgement with the database unreachable, (a) discards a token that a committed, active registration holds. Custody holds, but the database and the store disagree until the next rotation. (a) also keeps today's process-stop window: a stop anywhere between `put` and the park leaves a token with no row.
- **(b)'s residual is narrower.** Only a stop, or a failed handle write followed by a failed discard, between `put` and the handle leaves a token with no row. That window is one statement long.
- **(b) suits what comes next.** B2 builds the sweep next, so constraining it now costs nothing. And (b) needs no migration: `PendingTokenDiscard` already has `created_at`.

### 3.3 Three conditions on (b) (AN1)

The manager's six steps are right. Three points need to be exact before they hold under every interleaving:

1. **The save consumes its handle, or refuses.** The manager's step 3 says the transaction that saves the reference deletes its pending row. It must also refuse unless it deletes exactly that one row. Otherwise the sweep's safety rests only on its time bound: a command slower than the bound could save a reference the sweep has just discarded. With the check, the pending row's lock orders the two:
   - if the sweep's removal commits first, the command finds no row and refuses;
   - if the command's commits first, the sweep finds no row to take.

   The time bound is then only there to spare a running command a needless refusal.
2. **The handle refuses a reference already held.** The manager's last point says (b) "rests on" B1R-5. With one more check it no longer does: the handle is written only if no registration and no pending row already holds that reference. If one does, the store has broken its contract. The command refuses (`token_store_refused`) and discards nothing, since the reference belongs to someone else. A store that breaks B1R-5 then gets refused, not served a discard of a live token.
3. **Known and unknown outcomes, exactly.** The manager's step 4 names "a refusal, a replay, a conflict" as known; step 5 treats `done is None` as unknown. But `done is None` also covers a refusal and a deadlock, both of which rolled back, and a database error raised inside the transaction's body. That includes the one-active constraint's `IntegrityError` (case 9's race), which also rolled back. The rule `_run` can apply exactly:
   - **known:** a failure raised before the body returned;
   - **unknown:** a failure after the body returned, that is, at the commit.

   Known outcomes discard the reference at once; only an unknown one leaves the handle to the sweep.

### 3.4 D24's condition (AN2)

The sweep's part, as the manager framed it, with the order that makes condition 1 work:
- it takes a pending row only once it is older than the bound and no registration holds its reference;
- it removes that row in its own committed transaction *before* it calls the store, so a command can no longer save the reference;
- it writes the row again if the store's discard fails.

That keeps every external call out of a transaction, as P06.DB requires. B2's prompt names the bound.

### 3.5 What (b) leaves

- **A stop, or a double failure, in one statement's window.** A process that stops, or a handle write and a discard that both fail, between `put` and the handle leaves a token in the store and in no row. The double failure is logged with a fixed line. This is the recorded limit, narrowed from today's.
- **An unknown outcome waits for the sweep.** Its reference waits for the bound, then is discarded if no registration holds it.
- **A rotation keeps working.** B1R-5 still matters: a store that reused references would have its rotations with the same token refused (condition 2). The real store must meet it (carried to P09.2 and P11B), and its `discard` must change nothing for a reference already discarded, because the sweep and a refusing command can both discard one. The fixture meets both: `put` makes a new `uuid4` reference, and `discard` of an unknown reference changes nothing.
