## 3. Item 1 — F-2, the password-change guessing budget

**What 65.21.1 does** (each line read in the wheel):
- **The limit:** `ChangePasswordView` carries `rate_limit(action="change_password")` on `handle` (`headless/account/views.py:400`). `AuthenticatedAPIView.dispatch` refuses an unauthenticated request before `handle` runs (`headless/base/views.py:57-63`). So the limit sees only signed-in requests, keyed by the account (`core/internal/ratelimit.py:162-169`).
- **What it counts:** the decorator consumes before the view runs, on every request that is not a `GET`, whatever the outcome (`core/internal/ratelimit.py:242-276`, `:339-356`). That covers a wrong current password, a right one, and a new password that the validators refuse.
- **The check:** `ChangePasswordInput.clean_current_password` calls `self.user.check_password` only (`headless/account/inputs.py:180-184`). There is no `authenticate`, no `pre_authenticate`, no `login_failed` and no signal. Nor does the view have a reauthentication guard, so `ACCOUNT_REAUTHENTICATION_REQUIRED` does not reach it.
- **The setting:** `change_password` defaults to `5/m/user` (`account/app_settings.py:287`), and an override merges into the defaults (`:311`). `5/300s/user` parses as 5 per 300 seconds per account (`core/internal/ratelimit.py:95-121`).

**The budget per 300 seconds,** for a holder of a live session key or access token:

| | Sign-in form and `auth/reauthenticate` (`login_failed`, per address) | Password change (`change_password`, per account) | In all | Against the sign-in form's 5 |
|---|---|---|---|---|
| Today (`5/m/user`) | 5 | 25 | 30 | six times |
| (a) `5/300s/user` | 5 | 5 | 10 | twice |
| (c) `3/300s/user` | 5 | 3 | 8 | 1.6 times |
| (b) parity | 5 | none of its own | 5 | the same |

**Why (a):**
- **It is one setting** on allauth's own limiter, with no Glow code on this boundary. (b) would put Glow code ahead of allauth's route or around its view, on a security boundary, to remove the last factor of two.
- **The remainder is bounded** by what already limits a token holder:
  - a session lasts at most 30 days;
  - a replayed refresh token ends it;
  - the member's logout or password change ends it;
  - a right guess at the password change ends every session and sends the password-changed notice.
- **(c) gains little** (8 against 10) and costs members, since every signed-in request counts: at 3 per 300 seconds, a member whose new password the validators refuse twice has one try left for five minutes.
- **A second, daily window** on the same limiter would bring the long-run rate near the sign-in form's (65.21.1 keeps separate windows apart). I considered and rejected it. It adds a second number to every statement, and its test needs a clock moved across a day, for a remainder that is already bounded.
- **Not Nathan's.** The only change a member could notice is a wait of up to five minutes after five password-change attempts in a row, where allauth's default makes it one minute.

**C2.1 — D3's rate-limit bullet.** Replace the whole bullet that begins "allauth's rate limits keep their defaults (`ACCOUNT_RATE_LIMITS`). They use Django's cache:" with:

> - allauth's rate limits keep their defaults (`ACCOUNT_RATE_LIMITS`), except `change_password`, which is `5/300s/user`. At `account/password/change` a wrong current password is checked by `check_password` alone and consumes no `login_failed` (65.21.1, `headless/account/inputs.py:180-184`), so allauth's default `5/m/user` would give a holder of a live session key or access token five times the sign-in form's budget there. Every signed-in request there counts, whatever its outcome, a member's own included. So that holder gets 5 guesses per 300 seconds at the password change, besides the 5 the sign-in form and `auth/reauthenticate` share through `login_failed`: 10 in all, twice the sign-in form's. The threat model records that remainder. The limits use Django's cache: a local-memory cache in the proof; P11 needs a shared cache for more than one worker (carried to P11).
