## 3. Item 1 — CX9: correct it before the merge

**The defect is real, and the manager's verification holds in the code.**

- `revoke()` clears the conversation and publishes `revoked`, but does not advance `conversationEpoch`.
- `readHead()` and `loadOlder()` test only that epoch when a response returns. So:
  - a head page requested before the revocation runs `mergeHead` and publishes `ready`. `ConversationScreen` then leaves its revoked branch and shows the history and the composer again;
  - an older page puts its messages back into the store's state;
  - a read that fails without ending access publishes `error`, which also leaves the revoked branch.
- `run()` tests the same epoch, so a send outstanding at the revocation can still publish `sent` and start a new head read.
- `moveReadCursor()` tests it too, so a late cursor answer still sets `lastRead`.

**I also found one more path.** `readList()` tests only the owner's epoch. A list read outstanding at the revocation can therefore return the list as the server built it before the revocation, and put the revoked conversation's row back, with its unread count and latest time, until the next list read.

**Why (b), by DM-23's rule** (a defect in a stage's own code that misses an item of that stage's prompt is fixed before the stage merges):

- **It misses C2's item 3.** "An unmatch or a block … gives the conversation's revoked state". The session's record says the store drops a revoked conversation's history "at once, retained or shown". A late page undoes both after the revoked state has been shown.
- **It is the prompt's own fix-here class:** a finding that could "let a revoked member see a conversation's history or send in it". The composer comes back with the history.
- **It touches OD-12** ("after an unmatch or block neither person can send or see the conversation"). The server would refuse a send, but the app shows the conversation again after it has told the member it ended. That is more serious than CX8, which concerned only the member's own unread count.
- **A unit test can show it offline today,** by holding a read in `chatSetup`'s wrapper. It does not need P11's environment, as CX4 to CX7 did.
- **It differs from finding 3.** Finding 3 is history kept until a refusal is learned, a window only a real transport opens. CX9 undoes a refusal the store has already learned and shown.

**The manager answers Codex's thread** that the fix comes before the merge. CX9 does not join the P11 plan.

**The conditions** (the manager's b.1 to b.6, amended; C2-C2's prompt quotes them as written):

- **1.1 A revocation invalidates every request outstanding when it happens.**
  - The conversation's requests: a head read, a queued head read, an older page, a cursor command and a send.
  - The conversation list's read.
  - **A response to any of them, success or failure, changes nothing:** not the messages, the status, the older-page state, the cursors, `lastRead`, the draft, the send state or the list. It starts nothing either: no follow-up head read and no cursor command.
  - **A list response requested before the revocation does not put the revoked conversation's row back.**
  - The session chooses the mechanism (for example, advancing the conversation's epoch in `revoke()` and marking list reads issued before it) and records why.
- **1.2 No send is left pending.** After the revocation, the send state shows no pending send and offers no retry, whether a send was in flight or not. The revoked notice is the only state shown.
- **1.3 Requests issued after the revocation keep today's behaviour,** such as the read on a return to the foreground or after an authority change. The server decides them: a resumed match can legitimately become readable again (DM-22 3.1's interim rule).
- **1.4 Tests,** each with its reversal in a scratch copy outside the checkout, showing the test fails without the fix. Each holds a request through `chatSetup`'s transport wrapper, then revokes through a send's refusal and, separately, through a cursor command's.
  - **A held head read that then succeeds:** the conversation stays `revoked`, with no messages, no draft, no pending send, no new read and no cursor command.
  - **A held older page that then succeeds:** the store's messages stay empty.
  - **A held head read that then fails without ending access:** the status stays `revoked`, not `error`.
  - **A held send that then succeeds:** no `sent` state and no head read.
  - **A held cursor command that then succeeds:** no change to `lastRead` or the list.
  - **A held list read that returns the conversation:** the row stays absent.
  - **A read issued after the revocation, on a return to the foreground:** today's behaviour (1.3).
