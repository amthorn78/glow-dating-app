## 3. Findings

### D1 — Isolation: approved

The boundary is right:

- a separate package, its own settings and its own locks;
- `glow_persistence` imported unchanged;
- the API's guards and dummy backend untouched;
- a migration that fails on real PostgreSQL stopping the session as a finding, not being fixed in P06.DB;
- the reference design carried into the app by P06.2.

The refusal list is right to go beyond the API's `FORBIDDEN_CONNECTION_NAMES`, which names only `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` and `PGPASSWORD`. libpq also reads `PGPASSFILE`, `PGSERVICE`, `PGSERVICEFILE`, `PGSSLMODE`, `PGOPTIONS` and others, and its default files `~/.pgpass` and `pg_service.conf`. So the brief's "any `PG*` name" is the correct rule.

To cover the files too, the proof's settings give an explicit host, port, database name, user and `passfile`, with no service name, so that no libpq default is taken.

*Consider:*

- **A pin test.** The proof's lock pins the same Django as `services/api` (5.2.17), and an offline test fails if they differ, as the Stream proof job's pin test does. Without it, the proof and the app can drift apart silently.
- **`makemigrations --check --dry-run`,** run against the proof's settings. It shows that the reviewed migrations still match the models, which the "migrations apply" check alone does not.

### D2 — Dependencies: approved with conditions

- **`psycopg` 3:** right. It is Django 5.2's supported driver.
- **No allauth now:** right. DB09's partial evidence is about the app-side session lifecycle racing sends. That rests on `AccountSession`, `AppAccount.session_epoch` and the lock protocol, not on allauth's credential handling. Adopting allauth here would bring authentication forward under a proof, which PF01 §6's last rule warns against.

**Condition, on the claim:** the data model says `auth_session_ref` is "an adapter-provided non-secret library session identifier, not a session cookie/token/hash invented by Glow", and that "session metadata alone does not revoke a credential". The proof's random reference is a stand-in for that identifier. So the brief, the evidence record and the P11 plan's mark say:

- DB09 is partially evidenced **for the app-side session and epoch revocation ordering against sends**, with a stand-in session reference;
- **not** for maintained authentication, verification, recovery, linking, credential revocation or allauth, all of which stay with the item that serves authentication and with P11.

The reference design must not be carried into the app with the stand-in generator: P06.2 or the authentication item supplies the real identifier.

### D3 — The CI job: approved with conditions

**It is "CI-generated credentials" as PF01 means.** The password is created in the job, lives only in the job, protects a database that exists only in the job, and reaches no other system. Starting the container with `docker run` rather than a `services:` container is the right call for that reason.

**Safe enough,** with these conditions for the prompt:

1. **Masked before anything can print it.** The step generates the password with `set +x` in force, and its first output is `::add-mask::`. No step runs `docker inspect`, prints the container's environment or echoes the connection options. The password goes to the proof by a file readable only by the job's user (the proof's own name, or Django `OPTIONS["passfile"]`), never a `PG*` or `DATABASE_URL` name.
2. **Loopback only, and bounded.**
   - The container is bound with `-p 127.0.0.1:<port>:5432` and has a unique name.
   - The job waits for readiness with `pg_isready` and a fixed limit, and has a `timeout-minutes` like the other jobs.
   - An `if: always()` step removes the container. The job has no `env:` of secrets and uses the workflow's read-only permissions.
3. **The server settings the proof needs** go on the `docker run` command line and into the evidence: `-c track_commit_timestamp=on` (for condition 6.1), and the PostgreSQL version from `SELECT version()` next to the image digest.
4. **The gate.** It adds the job to `needs` and to the list of required jobs. On a documentation-only change the gate's own output stays "Ordinary documentation: application jobs intentionally skipped". The classifier is unchanged.

*Consider:* the proof connects as a non-superuser role that owns the proof's database, created in the job, so no case passes because of superuser privileges. Row locks behave the same either way, so this is hygiene, not a condition.

### D4 — Local runs: approved with conditions; within OD-17, not Nathan's

OD-17's constraints are:

- a disposable instance;
- no connection to a shared or production database;
- a record of what was tested;

"In CI" names where the evidence comes from. A disposable container in the implementation session's ephemeral cloud sandbox meets every constraint. PF01 §6 already allows the same kind of use for WordPress ("a disposable local CMS database is permitted as temporary development storage… Record that limited use"). The rule after §6 ("development convenience alone is insufficient") governs bringing the *app's* database integration forward. It does not govern where a proof iterates.

**Conditions:**

2. **Same recipe:** a generated password, loopback only, removed afterwards, and none of `DATABASE_URL`, `HD_API_KEY`, `GEO_API_KEY` or any `PG*` name present. It connects to no other database.
3. **If Docker does not work in the sandbox,** a throwaway PostgreSQL cluster started from a local binary (`initdb` in a temporary directory, listening only on a Unix socket or loopback) is the same thing under the same rules. The session records the version, since it may differ from CI's 17.x. If neither works, the session iterates through CI.

### D5 — The transaction design: approved with conditions

`READ COMMITTED` with `SELECT … FOR UPDATE` in a fixed order is the right choice. It matches the data model's unit-of-work table ("same revocation lock boundary"), and the account locks with `blocks_version` correctly protect the absent-block case, which is what DB06's P11 row asks for.

**What it can miss,** as written: six conditions for the prompt.

1. **Sign-out and session expiry must join the lock protocol.**
   - As written, sign-out updates only the `AccountSession` row. A send that read the session as valid before the sign-out, and commits after it, is a new authorization committed after a revocation. That is the exact case DB06 forbids, applied to DB09.
   - **Either** the send takes `FOR UPDATE` on its `AccountSession` row after the two accounts and the match (a fixed position in the order), and sign-out locks the same row. **Or** sign-out takes its account's row lock too, and bumps what the send checks.
   - The same holds for an administrative "expire" transition.
   - A forced interleaving tests it: the send waits holding locks while sign-out tries, and the reverse.
2. **Time is read after the locks, not at transaction start.**
   - PostgreSQL's `now()` is the transaction's start time. A send that waited on a lock can accept a session that expired while it waited.
   - The expiry check uses `clock_timestamp()` or `statement_timestamp()` after the locks are held, or a single time taken after locking.
   - A test covers a session that expires during the wait.
3. **One canonical lock order for every writer, whoever acts.**
   - A block by the higher account still locks the lower account first.
   - Account-wide revocations (suspension, deletion) lock the account row. They do **not** need to lock and bump every one of that account's matches, because the send checks both accounts' state and epoch under the account locks.
   - If the design does bump `contact_version` on each match, it locks those matches after the account, in primary-key order.
   - The brief states which it chose. A test runs opposing writers, a block by each side and a suspension against a send, and shows no deadlock and no violation. PostgreSQL's deadlock detector turning a design error into a retry would otherwise hide it.
4. **Idempotent retries: the order of checks, and concurrent duplicates.**
   - P11's row 138 says an identical retry by a *currently authorized* actor recovers the original receipt. So the order is: authorize the actor and session first, under the locks, then look up `(actor, idempotency_key)`.
   - A retry after a revocation gets a refusal, not the old receipt as if it were current. The brief's "returns the first result" needs that qualifier.
   - Two identical requests racing, neither yet committed, must yield one row. The second waits on the locks, then finds the first. A unique-constraint error on `message_dedup` must never reach the caller as a failure. Forced test.
5. **A locked read that finds no qualifying row is a refusal.**
   - Lock the rows by primary key, then check state in code. If a `FOR UPDATE` carries a `WHERE state = 'active'`, `READ COMMITTED` re-evaluates it against the newest row version and can return nothing; that must mean "refused", never "absent, so create".
   - Every value the checks use is read after the locks, inside the same `transaction.atomic()`. No model instance fetched before the lock is reused.
6. **The send's check list against the data model.** The UOW table says a send checks "current two-party eligibility/contact version".
   - The brief checks match state, blocks, account state, session and contact version. It does not say whether eligibility changes that are not suspension or deletion (a moderation restriction, consent withdrawal, a pause) refuse a send.
   - The brief either adds the ones current policy defines, the match's `restricted` state at least, or records the rest as excluded, with the reason (A05's policy is not set).
   - **Deletion** in the proof is the lifecycle transition (`deletion_pending` or `deleted`, the epoch bumped, the job and tombstone as the data model says), not a hard row delete. `CASCADE` would erase the committed authorization the proof must show was recorded.

*Soon or consider:*

- **Unblock does not resurrect.** After a block, an unblock with no new match, then a send with the old or the new contact version: refused (DB06, P11 rows 90 and 139 to 140; the data model's `Block` row).
- **`SERIALIZABLE`** gives its guarantee only if every participating transaction runs at that level, and it needs retry handling that P06.2 would then have to carry. Run it only as a recorded comparison, with its own negative control. Name `READ COMMITTED` with locks as the design P06.2 takes, so P06.2 does not inherit a choice.
- **The outbox:** the UOW table has the send commit its outbox event in the same transaction. If cheap, insert the `OutboxEvent` there so the proof shows it commits or rolls back with the authorization.

### 6 — The proof's honesty: approved with conditions

Forced interleavings, a stress run and negative controls are the right three parts. Three conditions make a pass trustworthy:

1. **A commit-order oracle.** "After the revocation commits, no new authorization commits" needs commit order, not call order or row timestamps.
   - With `track_commit_timestamp=on` (D3 condition 3), each row's commit time is `pg_xact_commit_timestamp(xmin)`.
   - The invariant check: no `MessageSubmission` commits after a revocation that makes it invalid. That covers a lower contact version, or its session or an account revoked earlier.
   - The stress run applies this check to every row, not only to what the test code believes happened.
2. **Proof that a forced wait happened.** A forced interleaving passes vacuously if the second transaction never actually waited.
   - Before releasing the first, the test confirms from `pg_stat_activity` (`wait_event_type = 'Lock'` for the second connection's backend) or `pg_locks` that the second is blocked.
   - The evidence records that each "while it holds the locks" case was observed waiting.
3. **Negative controls in the same CI run.**
   - Each broken variant runs in the final-head CI job and is shown failing there, not only locally.
   - A forced case's control fails deterministically. A stress control must fail at least once within its iteration budget, and the evidence records the first failing iteration.
   - The stress run records its seed, iterations and a measured overlap count, so "zero violations" is known not to come from races that never overlapped.

**What "partially evidenced" allows the records to claim:**

- **DB06:** on PostgreSQL 17, the reference design orders send authorizations against block, unmatch, suspension, deletion and (condition 5.1) sign-out, with the guarantees listed, under forced and randomized races.
- **DB09:** the app-side session and epoch revocation, as D2's condition words it.

**What it does not claim:**

- that the app enforces any of it. The design is in the proof, not the app, until P06.2 carries it and tests it again;
- the provider half;
- the P11 target, its roles, pooling or load;
- maintained authentication.

*Consider:* write the race suite against a small interface (send, block, unmatch, suspend, delete, sign out), so P06.2 runs the same suite against the app's adapter. That turns "carried into the app" into a check, not a claim.
