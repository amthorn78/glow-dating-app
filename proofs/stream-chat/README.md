# P06.1 Stream Chat permission proof

A sandbox harness that proves, against Nathan's development Stream application 1729640 and with synthetic users only, whether Stream Chat's permission model supports Glow's chat design:

- the app server controls channel membership and authorizes every send;
- a client never sends through Stream directly, because the app server sends on the user's behalf after its match and block check;
- a client's token lets it read its own current match's channel and nothing else.

Brief: [P06.1](../../docs/planning/p06-1-chat-provider-proof.md). Evidence: [2026-09-25 P06.1 evidence](../../docs/testing/evidence/2026-09-25-p06-1-chat-provider-proof.md).

This is proof tooling, not application code. It is outside the application runtime, and it sets no `GLOW_*` variable. It never touches a database, HDE or Railway.

## Variables

| Process | Reads | Never has |
|---|---|---|
| Server (`python -m glow_stream_proof`) | `STREAM_APP_ID`, `STREAM_API_KEY`, `STREAM_API_SECRET` from its own environment. It refuses to run if `DATABASE_URL`, `HD_API_KEY` or `GEO_API_KEY` is present (checked by name), or if `STREAM_APP_ID` is not `1729640` | — |
| Client (`node client/runner.cjs`) | `PROOF_API_KEY` (the client-safe API key), `PROOF_USER_TOKEN` (that session's own user token, if any), `PROOF_MAX_API_CALLS`, and the passthrough `PATH`, `HOME`, `LANG`, `HTTPS_PROXY`, `https_proxy`, `NODE_EXTRA_CA_CERTS` | `STREAM_API_SECRET`: the server builds the client environment from an allowlist and refuses one that contains the secret's name or value. The runner itself exits with code 3 if the name is present |

The harness never prints, logs or writes the secret or a full token:

- output passes through a redactor, and anything written is leak-checked first. The redactor also removes the application's API key from free text (P06.1-I2b: Stream's code-43 message quotes it); the key is client-safe, so its presence is not a leak, and the leak check does not refuse it;
- evidence shows token claims only;
- no tool that stores credentials (for example a Stream CLI login) is configured.

## Live commands

Every command reads `STREAM_*` from the server process's own environment. Commands that change the application are dry runs unless given `--apply`, except `run`.

```bash
.venv/bin/python -m glow_stream_proof baseline                 # read-only snapshot into .work/, without other users' identifiers or names
.venv/bin/python -m glow_stream_proof configure                # print the plan (dry run)
.venv/bin/python -m glow_stream_proof configure --apply        # apply, re-read and verify
.venv/bin/python -m glow_stream_proof run --accept-dashboard-user
.venv/bin/python -m glow_stream_proof run --accept-dashboard-user --only <case ids>   # a subset; product cases alone get the lean setup (P06.1-I2b)
.venv/bin/python -m glow_stream_proof verify-clean             # no proof users, channels, user groups, calls, feeds or activities remain; the standalone poll listing needs a user (see "Limits")
.venv/bin/python -m glow_stream_proof cleanup [--apply]        # hard-delete leftover proof users, channels, calls and feeds, and the proof users' Feeds data
.venv/bin/python -m glow_stream_proof restore [--apply] [--delete-match-type]   # --apply re-reads and verifies; chat only
.venv/bin/python -m glow_stream_proof probe-products           # P06.1-I2b, read-only: is each of Video and Feeds available? (one configuration read per product)
.venv/bin/python -m glow_stream_proof configure --products video,feeds            # P06.1-I2b: the differential Video and Feeds plan (dry run) and the chat verification
.venv/bin/python -m glow_stream_proof configure --products video,feeds --apply    # the one lasting change of P06.1-I2b; refuses in code unless chat verifies (see "The Video and Feeds lockdown")
.venv/bin/python -m glow_stream_proof record-products-baseline --snapshot .work/snapshot-<stamp>.json   # writes baseline/video-feeds-…json from a baseline snapshot; calls nothing
```

`run`:

1. Preflight. The run refuses unless the configuration verifies, and unless the application holds no data the run did not create. With `--accept-dashboard-user`, the run stops unless exactly one user has role `admin` and `custom.dashboard_user` true, and that user was created in the minute recorded for the user Nathan confirmed on 25 September 2026 (24 September 2026, 13:07 UTC). No identifier is recorded. That user is never changed or deleted, and only its role, dashboard flag and creation time are compared. (Corrected in P06.1-C1: at I1's head the flag accepted any number of dashboard-flagged administrators.) Since P06.1-I2b preflight also lists the calls, feeds and activities (`POST /api/v2/video/calls`, `POST /api/v2/feeds/feeds/query`, `POST /api/v2/feeds/activities/query`) and refuses the run when any exists, as it does for a channel. A listing that is not 2xx is "not available" only when the product's own configuration read says the product is not available (then no object of it can exist, and the run goes on); otherwise it is "not verified", whatever the listing's message says, and preflight refuses the run, as it does when the channels cannot be listed (the independent check of I2b, finding 3).
2. Setup. Creates synthetic users A, B, X and D (role `user`) with run-prefixed IDs, and issues each a 900-second token. Creates match channels AB and XD with exactly two members each. **A Video and Feeds run** (P06.1-I2b: `--only` naming product cases alone) gets the lean setup instead: users A and B with a token and a connected session each, no channel, no message; the authorized path and the reconnect check are not made, and the run says so. So run V1 and run V2 count 2 users and 2 connections each, and fit beside run 1 and its reserve.
3. The authorized path, then the bypass matrix with P06.1-I2a's cases among it (phases 15 to 65, on AB and XD), then the reconnect check, then the destructive cases, then P06.1-I2b's Video and Feeds cases (phases 91 and 92, on calls and feeds of the run's own), then P06.1-I2a's mechanism families (phases 100 to 106), each on users and a channel of its own. Before the first family the I1 matrix's client sessions are closed, so that the families stay within the connection guardrail; with `--only`, only when a family is among the cases.
4. Finish, whatever stopped the run (a stop condition, a guardrail, an error, a timeout or Ctrl-C):
   - every temporary change still in the journal is restored and verified (see below). A restore that fails is tried again after 10 s and 20 s when the failure was a rate limit (HTTP 429 or Stream code 9) or not a stop signal at all (for example a 5xx, or a re-read that still shows the change). After any other stop signal (a charge signal, or the API-call budget) it is not tried again (changed in P06.1-C2: until then every charge signal was retried). A restore that was made and accepted, but whose verification could not be made, leaves the journal and is reported **not verified**, not "not restored" (P06.1-C2);
   - the client processes close, and each reports what its SDK sent after the last command (P06.1-I2a);
   - cleanup, unless a charge or limit signal was met anywhere in the run: as the run's own stop, behind another stop kept as the run's stop, replaced in flight by a Ctrl-C or an error, by these restores, or as a client process closed (P06.1-I2a). The run records every such signal (`stop_signals` in the results; see "Budget guardrails"), and after one it deletes nothing; the problem "cleanup skipped: …" names the signal and what to do by its kind (changed in P06.1-C3: until then only the run's own stop counted, so a signal first met by the end of the run did not stop the cleanup; the rule by kind since P06.1-I2a). Otherwise cleanup hard-deletes the run's polls and user groups (including any a client managed to create), its Video and Feeds objects (every reaction, comment, activity, follow, feed and call it created or recorded, then each run user's Feeds data with Stream's `POST /api/v2/feeds/users/{id}/delete`, when the run touched Feeds at all; P06.1-I2b), its channels and its users, including any user whose ID contains the run prefix (Stream prefixes guest IDs), and the `deleted-user-1729640-…` system user Stream creates during that delete. Each step is guarded, so a failure is recorded and the next step still runs, except a charge or limit signal, which ends the cleanup at once and is recorded too. It then confirms that no proof user or channel remains, no poll or user group that was not already there at preflight (preflight lists them; only counts are shown), and no call, feed or activity (P06.1-I2b: a product object's delete must be 2xx, or 404 for one the case's undo already removed, and its delete task, when Stream gives one, must complete);
   - the configuration is re-read and compared with the target (`configuration.verify()`).

It prints the redacted results table and writes `.work/run-<prefix>.json` and `.md`, with progress after every case. The results also list every stop recorded, every charge or limit signal met (P06.1-C3), any temporary change not restored or not verified, and every problem found after the run. `run-<prefix>.json` is first written before the end of the run starts (marked `end_of_run: not finished`) and rewritten when it ends, so a second Ctrl-C inside the end of the run loses nothing observed (every `.work` file is written through a temporary file and then renamed, so an interrupted write leaves the previous file whole; the usage ledger too since P06.1-C3); that Ctrl-C stops the end of the run, closes the client processes, writes the results with the problem "the end of the run was interrupted", keeping every problem the end of the run had already found, and exits 2 (P06.1-C2). If writing the results before the end of the run fails, the note saying so is redacted (P06.1-C3).

A case interrupted before it finished (a guardrail stop, a failed restore, an ended client session, any other exception or Ctrl-C) still records its row, with what it had observed: a FAIL stays a FAIL, and anything else becomes INCONCLUSIVE with the interruption as its reason (P06.1-C2; until then only a failed restore kept the row). See "Interrupted cases" under "Verdict rules".

Exit codes of `run`: `0` only if the run completed, every temporary change was restored and verified, cleanup was complete (every delete task `completed`, nothing left) and the configuration verifies; `2` if the run stopped (the output says why, and lists anything found after the run); `4` if it completed but a check after it failed or could not be made, including a cleanup skipped because the end of the run met a charge or limit signal.

If the output reports a temporary change not restored, `configure` (a dry run) shows what differs from the target, and `configure --apply` returns guest creation and every `glow-match` feature to it. `restore --apply` does not: it returns the recorded pre-proof baseline. AB's overrides end with AB's deletion.

## Verdict rules

The matrix quality rule is unchanged: a refusal counts only when Stream returns its authentication or permission error, and every negative case pairs with a positive control. P06.1-C1 made these rules explicit and stricter, and P06.1-C2 and P06.1-C3 stricter again; no HOLDS rule is weaker than at I1's head. Two FAIL rules now need their evidence (P06.1-C2): E5 with an unreadable stored user, and T4-rest-unread without both controls, are INCONCLUSIVE instead of FAIL, which is still not a pass. Since P06.1-C3 RT2 and RT3 follow the quality rule too: a feature refusal is REFUSED (feature off), and an authentication or permission refusal HOLDS only with a successful control of the same request.

- **Stream's answer, not the SDK's error** (new in P06.1-C1). The status and code are those of Stream's recorded response to the request under test: the one HTTP request the command sent. The SDK's own error is never used. A command that sent no request, or whose request has no recorded response (a local SDK throw, or a call that returned without sending), is **INCONCLUSIVE**, never HOLDS. Every command judged this way must send exactly one request; a reply with more than one recorded request has no answer either (P06.1-C2). The row of a case whose command recorded more than one request lists each request's method, generic path and status in its detail (`requests`), and in a generic case a 2xx among them is undone like any client success, in the production phase of a feature-gated case too (P06.1-C3; until then the statuses were dropped and the 2xx was not undone). A positive control counts only if Stream's recorded answer to it was 2xx.
- **WebSocket connects.** Success is the handshake Stream sent. A refusal counts only when the SDK built the error from Stream's own error frame; any other connect failure has no recorded answer.
- **Token refusals** are 401 with Stream code 5, 40, 41, 42 or 43. Code 2 is Stream's API-key error, so it is not attributable to the token (changed in P06.1-C1). Permission refusals are 403 with code 17 or 70.
- **HOLDS:** an attributable 401 or 403 and a successful control.
- **HOLDS (filtered, not refused):** 2xx without any of the case's leak terms, while the control found them. The guest and anonymous `read-ab` terms include AB's ID, A's and B's IDs and names, and both message IDs as well as their text; the `message` terms include XD's message ID, X's ID and XD's ID (widened in P06.1-C1).
- **HOLDS (accepted, not applied):** 2xx, but the claim or change had no effect. For E5 and S14 both the stored user and the connection's own user object in Stream's handshake must be unchanged (P06.1-C1); a change in either is a FAIL. If A's stored user cannot be read (Stream does not answer the listing with 2xx, or the listing does not include A), the case is INCONCLUSIVE, "A's stored user could not be read", unless the connection's user object already showed the change, which is a FAIL (P06.1-C2; until then an unreadable E5 user counted as a changed role, a FAIL, and an unreadable S14 user as unchanged). The run then stops once the row is recorded, because A's stored role or profile is unknown (P06.1-C3; until then a listing Stream did not answer with 2xx raised, the row read "harness error", and the run went on, as it did after a listing without A).
- **REFUSED (feature off; not a permission error):** a 400 feature error (code 18 or 19).
- **INCONCLUSIVE:** no recorded answer, a refusal that is not attributable, a control that did not succeed, a client session ended by a timeout or a mismatched reply, or a case interrupted before it finished without an observed FAIL.
- **FAIL:** the action succeeded, or a response disclosed a leak term.

Cases with their own rule:

- **Interrupted cases** (P06.1-C2). Every way a case can end records its row: a guardrail stop, a failed restore, an ended client session, any other exception or Ctrl-C. The row keeps what the case had observed before the interruption (its request, Stream's answer and any evidence); a FAIL stays a FAIL, and anything else becomes INCONCLUSIVE, "interrupted before the case finished: …". The detail names the interruption. With nothing observed yet, the row is INCONCLUSIVE with the interruption as its reason. A guardrail stop, a failed restore and Ctrl-C then stop the run; after an ended client session or a harness error the run goes on, unless a charge or limit signal was met, whose stop that error replaced (P06.1-C3). A progress file that cannot be written while a stop is in flight is noted and never replaces the stop.
- **A client success that must be undone** (P06.1-C2). When a client action that must be refused succeeds (in a generic case, a 2xx to any request its command recorded; P06.1-C3), the case's undo requests reverse it after the control, and the row records each undo's status. If the control is interrupted first, the undo follows the rule for what may still run after each kind of stop: after a guardrail stop it is not made (a charge or limit signal stops the run at once and deletes none of its data; the API-call budget has no calls left), and after Ctrl-C it is not made; after anything else (an ended client session, a failed restore, a harness error) it is made, unless a charge or limit signal was recorded in the run (P06.1-C3). The row says which, and why. The change is always to the run's own synthetic users, channels, messages, polls or groups, which cleanup deletes (after a charge or limit signal, `cleanup --apply`).
- **Feature-gated cases** (S2, S5, S6, S7 and S12; S10's poll vote only where said). The feature-on phase is judged as above. If the request enabling the feature was not answered with 2xx, the case (S2, S5, S6, S7 or S12) is INCONCLUSIVE, "could not enable …", unless the feature-on phase already showed a FAIL, which stands: the client's action succeeded, whatever the configuration was (P06.1-C3; until then the failed enabling request turned that FAIL into INCONCLUSIVE). The same request is then sent under the production configuration, where it must also fail: a success there is a FAIL, and a request with no recorded answer is INCONCLUSIVE, "no answer from Stream was recorded for the request under the production configuration", unless the feature-on phase already showed a FAIL (P06.1-C2); this much holds for S10's vote too. If the production command of S2, S5, S6, S7 or S12 recorded more than one request, the row lists them too, and a 2xx among them is undone (P06.1-C3); that undo's note is added to the feature-on phase's, labelled `production:`, never written over it (P06.1-I2a; the C3 review's nit 4). S10 neither judges its enabling request's status nor undoes a success: its vote HOLDS only when the server's identical vote succeeded, which needs polls on (corrected in P06.1-I2a: until then this rule named S10 among the cases that follow all of it; the C3 review's nit 3). S10's setup is new in P06.1-I2a (the I1 review's finding 6: polls turned on for the type did not reach AB within 3 s in I1): B's poll message goes to a channel of S10's own, created while polls are on, and is sent again, up to 10 times 3 s apart, while Stream answers that polls are not enabled for the channel; the control records how many attempts it took. Stream documents no channel-level override for polls.

- **G1:** judged on the client's own `POST /guest`, which must be the one HTTP request the command recorded (P06.1-C2). It FAILs whenever that request created a guest, whatever the connect `setGuestUser` makes afterwards did (P06.1-C1).
- **G2** (new setup in P06.1-I2a; the I1 review's finding 6): the guest is created server-side (`ServerApi.create_guest`, `POST /guest`) and connects with its ID only, with the access token Stream returned (never printed or written); G1's control's guest is not used, because the lockdown refuses the connect `setGuestUser` makes. If Stream refuses the creation while guest creation is disabled, with any status (its documentation does not say which; the independent review, a nit: until then only a 403 was tried again), the setting is enabled for that moment, journalled, and disabled again and verified, as for G1's control. Each G2 row's detail records the setup (`g2_setup`): the creation's answers, the stored ID's form, the guest's role and its connect. Without a connected guest the rows are "not run", INCONCLUSIVE. The probes are judged as before.
- **G3:** INCONCLUSIVE unless the anonymous connect succeeded, because the SDK otherwise rethrows the connect's error for every probe without sending anything (P06.1-C1).
- **RT1** (no refusal involved): HOLDS when A received AB's event and nothing about XD while X received XD's event; FAIL if any event A received carries XD's ID or text.
- **RT2 and RT3** ask what reaches B. FAIL if any event Stream delivered to B, of any type, in any window collected (after A's request and after the probe), carries the marker (P06.1-C1: every window and every event type is searched). Otherwise:
  - INCONCLUSIVE if A's request has no recorded answer, or B's listener did not see the probe message;
  - if Stream accepted the request: HOLDS if the named events arrived without the marker, and HOLDS (accepted, not applied) if none arrived;
  - if Stream refused it with a feature error (400 with code 18 or 19): REFUSED (feature off; not a permission error), as for every other case (changed in P06.1-C3: until then HOLDS; I1's recorded RT2, 400 code 18, stays as recorded);
  - if Stream refused it with an authentication or permission error (401 with a token code, 403 with code 17 or 70): HOLDS only when the same request, by a member allowed to make it, succeeded, and nothing carrying the marker reached B while B was listening (P06.1-C3; until then HOLDS without a control). For RT3 that control is B's own `markRead` with the same body, sent after both windows are collected, and it counts only if its recorded request has the same method and path as A's; the control's own events are collected apart and recorded by type (`control_event_types`), and that window is searched for the marker too, leaving out only B's own read events: type `message.read` or `notification.mark_read` whose `user.id` is B's (changed in P06.1-I2a: until then the whole control window went unsearched). A control that does not succeed leaves the case INCONCLUSIVE. RT2 has no such control: no member may send a typing event while typing events are off, so its refusal is INCONCLUSIVE, "no positive control";
  - if Stream refused it any other way (`input`, `not-found` or `other`: a 400 input error, a 404, a 5xx): INCONCLUSIVE, "refusal not attributable". A malformed request or an outage says nothing about what a well-formed event delivers (changed in P06.1-C2: until then any refusal, and any named event after a refusal, was HOLDS).
- **Events** count only when Stream delivered them. The SDK's local events (`channels.queried`, `capabilities.changed`, `connection.changed`, `message.read_locally` and the rest of stream-chat 9.53.0's local list, plus health checks) are dropped, and the event type that carried a marker is recorded (P06.1-C1).
- **T4-ws:** Stream authenticating the connection as the token's user, not the claimed one, is HOLDS (accepted, not applied).
- **T4-rest-unread:** neither kind of HOLDS unless A's and B's own identical requests succeeded (the controls). A refusal of the claim HOLDS only with both controls (P06.1-C1). An accepted claim needs both controls and all three unread totals (A's, B's and the claim's, each from a 2xx answer) and A's and B's totals must differ: the claim's total equal to A's is HOLDS (accepted, not applied), equal to B's is a FAIL, anything else INCONCLUSIVE. Without both controls or all three totals the case is INCONCLUSIVE (P06.1-C2; until then a failed control or a missing total could give HOLDS (accepted, not applied) or a FAIL).
- **S15:** FAIL if B reads the marker by any of its reads; the result names each read, and for events the event type. A's member field is unset after each phase, however the phase ends, except after a guardrail stop or once a charge or limit signal has been recorded, whatever stop is in flight: then no unset is sent, the run's notes say so (and the row's detail, `member_field_unset`, once the case has observed something), and cleanup deletes A (after a charge or limit signal, `cleanup --apply`) (P06.1-C3; until then the unset was sent after a charge signal too).

### P06.1-I2a cases

These rules were written before any live run of these cases.

**The mechanisms** (`RV-remove`, `RV-ban`, `RV-hide`, `RV-freeze`, `RV-revoke`, `SD-deactivate`, `SD-delete`; `glow_stream_proof/mechanisms.py`). Nathan's history policy (OD-12): after an unmatch or block, neither person can send or see the conversation, and the history is kept out of sight only for safety reports.

- **Setup.** Each mechanism has a channel of its own. The four channel-level mechanisms (removal, a channel ban, hide, freeze) each act on their own channel, whose members are the same two synthetic users, M1 (the member acted on) and M2 (the other member). The three account-level mechanisms each act on a user of their own: R (per-user token revocation, with two devices, that is two client sessions), S (deactivation) and H (a hard delete), with M2 as the other member. So no channel is shared between mechanisms, and no user is acted on by two mechanisms: M1 is acted on only in channels of its own, one per mechanism, and M2 only by the freeze (DM-04 finding 5; revision 1 of the I2a prompt: "Channel-scoped mechanisms can share users on separate channels; user-scoped ones ... need their own users"). Each family's controls, made before its mechanism, show that no earlier family reached its channel.
- **What is recorded, for each member, before and after the mechanism, by the same member** (the control is the same request succeeding before the mechanism):
  - `rest`: a read of the channel (`channel.query`) by the member's existing session;
  - `ws`: whether the member's already-open WebSocket subscription receives the channel's events after the mechanism: a server-side channel update (`channel.updated`) and a message from M2 (`message.new`). Each session's events are collected in one window, the members the mechanism does not act on (the listeners) first and the members it acts on last; a member that missed the probe while another session received it is collected a second time, so a late delivery is not taken for an ended subscription (the independent review, point 2);
  - `token_reuse`: a new session with the member's existing token connects and reads the channel;
  - `s15`: the member's own `updateMemberPartial` write on its membership;
  - `token_issued_after`, for the account-level mechanisms only: a new session with a token issued for the member after the mechanism connects and reads the channel. For the revocation it is the token issued past the `iat` back-dating (below); for deactivation and the hard delete, a token issued at once (the independent review, point 4).
- **A dimension is `ended`** only on Stream's authentication or permission error (401 with a token code, 403 with code 17 or 70), recorded by status and code, after the same request by the same member succeeded before the mechanism; **`not ended`** when it still succeeds; **`not shown`** otherwise (no control, no answer, a 404 or 400, an outage). **A 404 with Stream code 16 counts as `ended` too** (P06.1-I2b; the manager's decision on I2a, as its review refined it), but only when all three hold: the same request by the same member succeeded before the mechanism; the other member's identical request, already collected, still succeeds after it (for the token dimensions, the other member's new session connects and reads); and Stream's message, kept in the row (`after.<member>.messages`), names the missing membership or user (the member's own ID, or "member" after a removal, "user" or "deactivated" after a deactivation). It applies only where the mechanism removes what the request needs: the membership after a removal (RV-remove), the user after a deactivation (SD-deactivate). Otherwise the dimension stays `not shown`, with Stream's message in its reason. The subscription is `ended` only when the member's open connection received none of the probe's events, in either of its windows, while a listener (the other member, or for a freeze the member acted on and the other in turn) received them; if nothing reached anyone, it is `not shown`, because a slow delivery is not an ended subscription. It is also `not shown` when the member's connection changed after the mechanism in a way that could explain the miss, as the SDK's own `connection.changed` (offline or online) and `connection.recovered` events show, in the window of the mechanism or the probe's: for a channel-level mechanism, which is not expected to touch connections, any close or recovery; for an account-level one, a recovery (closing the member's connections may be the mechanism itself, and the row then says the connection closed). Token reuse, and a token issued after the mechanism, are `ended` when the new session's connect, or its read of the channel, gets such an error. A member whose client session ends (a timeout, a mismatched reply, an exit) has its remaining dimensions `not shown`, naming the end; the family goes on without it, and stops only at a step that needs that session (the independent review, point 7). What a family has observed is judged and kept as its row after every part of a step, however that part ends (P06.1-I2b; the I2a review's finding 1): a stop on one member's request inside a step no longer loses another member's observation, so a `not ended` read seen before the stop stays in the row as DOES NOT MEET, and once the mechanism's request is answered the row says so (`applied: …`).
- **Token lifetime** (the independent review, a nit). A refusal must never be a token's own expiry: every token is issued for 900 s, and a family runs only while M1's and M2's tokens, issued by the first family, have at least 300 s left (a family takes about a minute); otherwise it is not run, INCONCLUSIVE. A dimension counts as `ended` only while the member's own token had at least 60 s left when the observations after the mechanism ended; the row records each token's seconds left (`token_seconds_left_after`). In the same way a case before the families runs only while the setup tokens (A, B, X and D) have at least 120 s left (the longest such case takes about 40 s), and the reconnect check (AP11) is not made otherwise, which is recorded as not passed.
- **The verdict.** **MEETS the history policy** when every dimension of the mechanism (the four above, and for an account-level mechanism `token_issued_after`) is `ended` for the member it is applied to (for a freeze, both members), its own client cannot undo it (below), and a server-side read still finds the channel's first message (retention). **DOES NOT MEET the history policy** when a dimension is `not ended`, the member's client undid it, or the messages are gone. Otherwise **INCONCLUSIVE**, naming what was not shown. A mechanism Stream refuses to apply is INCONCLUSIVE, "Stream did not apply the mechanism", and the run goes on. Whether a mechanism meets the policy when applied to both members is derived from the member it is applied to (by symmetry); only the freeze is judged for both. What a family has shown is kept as its row after each step, so a family interrupted later keeps a DOES NOT MEET, as a case keeps a FAIL; anything else becomes INCONCLUSIVE (the independent review, point 7).
- **The member's own undo** (channel-level mechanisms; DM-04 finding 6): the member's client sends the request that would undo it (rejoin with `addMembers` of itself, `unbanUser` of itself, `show`, or `updatePartial` unfreezing). Its control is the server's replay of the same request, which undoes the mechanism, and it runs last. Stream documents that a new message ends a hide, and the probe's message does so; so the server hides the channel again before the member's own `show` (`hidden_again_before_undo`). If that hide is not answered with 2xx, or the member's channel list still shows the channel, the `show` is not sent and the undo is INCONCLUSIVE: a `show` of a channel that is not hidden proves nothing (the independent review, a nit). It is judged as any refused request: HOLDS (the client cannot undo it) on an authentication or permission error with a successful control; FAIL (the client undid it) on a success.
- **What each member is shown** (DM-04 finding 6): the event types each member receives when the mechanism is applied, the SDK's local events excluded; any message the channel gains then that is a system message or was not sent by the run (a server-side read); and where M2's ID or name appears in them, leaving out lists of members, watchers and reads. The server names M2 as the acting user for the removal (`user_id`), the ban (`banned_by_id`) and the freeze (`user_id`), as an app acting for the member who unmatched or blocked would, so the record shows whether Stream passes that on. If Stream refuses the mechanism with a 403 when M2 is named, it is sent again without the acting user, and the row records both answers (`refused_with_the_actor_named`). The hide, and the account-level mechanisms, name no acting user.
- **Send versus revocation, on the provider side** (DM-04 finding 9(a)). After each mechanism the app records the unmatch or block in its own state (the fixture `MatchState`), and its send path must refuse both members' sends without calling Stream: check `AP12-<mechanism>`, PASS only with no API call. Then the server sends a message on the affected member's behalf. Server-side calls bypass Stream's permission checks, so Stream's answer to that send is **an observation, not a verdict**: it is recorded in the row's detail (`server_send_as_affected`) and judges nothing. The database-level ordering of a send against a revocation is P11's DB06; the proof claims nothing about it.
- **Per-user token revocation.** The server sets R's `revoke_tokens_issued_before` to the current second with a partial user update (`PATCH /api/v2/users`); an application-wide revocation is never sent (the guard refuses it). R's two devices hold tokens issued before it. Right after the revocation a new token is issued: the server SDK back-dates `iat` by 5 s, so its `iat` falls before the revocation time and it is refused by design (DM-04 finding 9(b)). Once the back-dating has passed (7 s after the revocation time) another is issued, which Stream's documentation says is accepted: it is the revocation's `token_issued_after`. If it connects and reads the channel, the revocation alone does not end the member's access, and the family DOES NOT MEET the policy on its own; ending access then rests with the app's token issuance (P06.2). The record gives each token's `iat` minus the revocation time, and each new token's connect and read. (Corrected in P06.1-I2a after the independent review, point 4: until then the late token was recorded but not judged, so the revocation could MEET the policy while that token read the channel.)
- **Suspension and deletion.** Stream's documentation does not use the word "suspend"; its mechanism for stopping a user's requests and connections while keeping its data, reversibly, is deactivation (`POST /api/v2/users/{id}/deactivate`, sent with `mark_messages_deleted: false`). The hard delete is `POST /api/v2/users/delete` with `user`, `messages` and `conversations` all `hard`: Stream requires `messages` and `conversations` to be `hard` when `user` is, and deletes every channel of two or fewer members where one member is the deleted user. The record gives what each does to the user's messages and to its member custom data (a server-side read of the channel and its members). If the hard delete's task does not report completion, the family is INCONCLUSIVE, whatever it observed: its observations may predate the delete (the independent review, a nit). A hard-deleted user, and a channel the delete removed, are taken off the run's record, so cleanup does not name them again: the cleanup's batch user delete leaves out a recorded user that its complete listing (deactivated users included) no longer shows, and a channel the delete may remove later is read first and left out if it is gone. Other channels are named by ID without a read, because a soft-deleted channel (C13's control) is not listed but must still be hard-deleted. The delete's channel is recorded as one that may be gone before the delete is sent, so a run stopped while it waits for the delete's task still reads it first (the independent review, point 8). A connect as H after the delete (its token reuse, or the token issued after it) may create the user again: such a connect is recorded (`connected_after_the_delete`), and H is named at cleanup again, where the prefix scan would also find it.
- **Cleanup** removes every state a mechanism leaves: the channels (banned, hidden, frozen) are hard-deleted by ID, the users (revoked, deactivated) are listed with `include_deactivated_users` and hard-deleted, and the `deleted-user-1729640-…` user the hard delete creates is deleted as before.

**The other cases** (`glow_stream_proof/i2a.py` and the matrix):

- **TD-expiry** (tokens and devices): a second client session of A (a second device) with a token that expires after 25 s reads AB, keeps a connection and, past its expiry, reads and reconnects; A's first device reads alongside. HOLDS when the expired token's read and reconnection both get an authentication or permission error after the same requests succeeded before expiry, and the controls finished at least 3 s before the token's `exp`; FAIL when either succeeds after expiry; INCONCLUSIVE otherwise, including a token without an `exp` claim. The row records how long before `exp` the control read finished, and `exp` minus `iat`, which is the lifetime plus the 5 s the server SDK back-dates `iat` by. Whether the open connection still received a message after expiry, and whether the first device still reads, are recorded, not judged.
- **OUT-send** (the outage, injected inside the process only; DM-04 finding 3): a second server client whose `httpx` transport raises `httpx.ConnectError` for every request, so the SDK's error path runs and no request leaves the process; no address is used. The app send path must refuse with no partial state. HOLDS when the send is refused with the provider's connection error, no message ID is kept, the match state and the run's record of messages are unchanged, a server-side read finds no such message, the transport saw exactly the one request, and the same send with the provider reachable then succeeds (the control). FAIL when anything of the send was kept or the path raised instead of refusing. No real outage is claimed.
- **S15-map** (the S15 mapping): for each member field (the custom `glow_note`, `pinned`, `archived`, `notifications_muted`, `channel_role`, `is_moderator`, `banned`, `shadow_banned`, `invited`), A's own write, whether the server then stores it, what B receives in its events and channel read, and, for a refused write, the server's replay of the same request (its control). Then the server overwrites and clears A's custom data. Its verdict is **RECORDED (a mapping, not a verdict)**. The three `member_custom_on_*` settings are read live at preflight and must be false (`configuration.verify`); the row repeats the values read.
- **Putting A's member record back** (S15-map, F9-pin and F9-archive; the independent review, point 1). A's member record in AB is read server-side before anything is written; if it cannot be read, nothing is written and the case is INCONCLUSIVE. A write may have changed the record unless Stream refused it with an input, feature or not-found error; after an authentication or permission refusal the server's replay may have. When its field (or the case) ends, however it ends (an answer, an error, an ended client session, Ctrl-C), A's record is read: each field written that differs from the original is put back (every field written, if the record cannot be read), and the record is read again and compared with the original in every mapped field. A field that already reads as it was is not written again, so a write Stream accepted but ignored needs no restore that it might refuse. A record that cannot be read, or does not match, stops the run after the case's row is recorded. After a guardrail stop, or once a charge or limit signal is recorded, nothing more is sent: the fields stay as they are, the row says so, and cleanup (after a signal, `cleanup --apply`) deletes A. An interrupted case keeps the field in progress and its restore in its row. (Corrected in P06.1-I2a: until the review, a write the server's control had applied, or one interrupted before its field ended, was not put back, and only the field written was compared.)
- **F9-pin and F9-archive:** A pins or archives AB for itself. FAIL when B's channel read or events show A's flag. HOLDS (filtered, not refused) only when a 2xx server read of A's record shows the flag and B's 2xx channel read returned A's member record without it, and B's events do not show it; HOLDS (accepted, not applied) only when a 2xx server read shows no flag after an accepted write; on an authentication or permission refusal, HOLDS when the server's replay of the same request succeeds. INCONCLUSIVE otherwise: A's record unreadable after the write, B's read refused or without A's member record (so it could not show the flag), or the flag already set (the independent review, point 5).
- **F9-invite-accept and F9-invite-reject:** B, invited to a channel of A's own, accepts or rejects with a message. FAIL when B's request succeeds, or its text reaches A or is stored (both read before the control); on an authentication or permission refusal, HOLDS when the server's replay of the same request succeeds.
- **The finding-9 reads** (`F9-replies`, `F9-reactions`, `F9-by-id`, `F9-query-reactions`, `F9-thread`, `F9-history`): A's request about XD's message must be refused. A 2xx is a FAIL even without data, because the endpoint did not refuse a non-member; the row says whether data was disclosed. The control is X's identical request, except for `F9-history`, a server-side API in Stream's documentation, whose control is the server's replay. `F9-sync` is a no-leak case: HOLDS (filtered, not refused) when A's sync returns none of XD's data while X's identical sync returns it. **The disclosure rule** (P06.1-I2b; the manager's decision on I2a, with its review's detail), for every case with leak terms: a term that appears, as a substring, anywhere in the serialized request the client sent (its path, query and body) is left out of the scan, because the sender already had it; `F9-sync` carries XD's ID inside the cid string, and `F9-thread`'s 404 names the message ID A sent in the path. The row's `disclosure` detail keeps the terms the request carried (`terms_in_the_request`) and, for each term found, the key names of where it was found (`found_at`). **When the request carried every one of the case's leak terms, nothing is left to scan** (P06.1-C4; the I2b review's nit 4): a success is then **INCONCLUSIVE** ("succeeded, but its own request carried every leak term, so nothing was left to scan"), never HOLDS (filtered), and the row's `disclosure` detail says `nothing_scanned: true`; a refusal keeps its own rule. No current case is so: every no-leak case with a step leaves at least one term to scan (`tests/test_answers.py`, `DisclosureRuleTest`), so no recorded verdict changes. The rule filters an echoed identifier even where the echo itself could signal that the object exists (a queried ID, or a cid in `inaccessible_cids`); that question belongs to the existence-oracle cases below, not to the disclosure rule (the I2b review's assessment note).
- **The other finding-9 cases** are generic cases under the rules above: `F9-ai` (an AI state event with free text; custom events are enabled on the type for its permission-layer phase, as for S12), `F9-member-other` (A writes B's membership), `F9-ban` and `F9-shadowban` (A bans B in AB), and `F9-leave` (A leaves AB with a message). Each control is the server's replay, and each undo is defined (the member field unset, the ban lifted, A added back to AB).
- **The existence oracle** (`EO-channel`, `EO-user`, `EO-message`): A's request for an existing ID is compared with the same request for an ID that does not exist: for channels, a query, a watch, a GET of the channel (the documented Get Channel, through the runner's GET-only `get` op) and a `sync` of its cid (P06.1-I2b); for users, a query and an add to AB; for messages, a fetch by ID. Two answers are identical when their status, Stream code and message match with the IDs replaced; two successes when their shape matches: the key names at every level, each list's length and each scalar's type, with `duration` left out, never their size (P06.1-I2b; the I2a review's finding 2: every Stream response carries a `duration` whose length varies). Each pair keeps both normalized answers in the row (`existing_normalized`, `missing_normalized`), so a FAIL on the text can be read. Each pair is judged on its own (the independent review, point 6): it is INCONCLUSIVE when either answer is not one Stream gave and the harness classified (no answer recorded, a local SDK error, or an unclassified status); FAIL (an existence oracle) when the two differ; HOLDS when they are identical refusals for authentication or permission, identical 404s or identical successes; INCONCLUSIVE when they are identical input or feature errors, which may come before any existence check. The case is FAIL when any pair is; HOLDS when every pair holds and an entitled read shows the existing ID exists (a control that does not succeed leaves it INCONCLUSIVE); INCONCLUSIVE otherwise. A 5xx is not a determinate answer, so two 5xx answers that differ are INCONCLUSIVE, not an oracle. What each pair shows is kept as the row as it is made, so an oracle seen before an interruption stays a FAIL. A probe that creates the missing channel is counted, recorded and deleted at cleanup.

### P06.1-I2b cases: Video and Feeds

These rules were written before any live run of these cases. The brief: "Video and Feeds: what a user token can do, and a lockdown by configuration only. No media session, no push, nothing that could incur a charge." Glow uses neither product; the same user token reaches both, and Stream's server SDK sends every product's requests to the one chat host, which the runner uses too.

- **The cases** (`VD-*`, group `video`; `FD-*`, group `feeds`; `glow_stream_proof/matrix.py`, `_products`) are generic cases under the rules above: each is one request a modified client can send with its own user token, through the runner's `product` op, whose allowlist and deny-list are in code (`client/product-op.cjs`; see "The guard"). Video: A creates a call of the `default` type, and one of the built-in `development` type, with custom data and A and B as members (`VD-create`, `VD-create-dev`); A reads, updates the custom data of, and sends a custom event with free text to a call the server created with A and B as members (`VD-read`, `VD-update`, `VD-event`); A adds B to a call of A's own (`VD-members`); B reads a call of A's that B is not a member of, and queries the calls A created (`VD-read-other`, `VD-query`, no-leak cases). Feeds: A creates its own feed with custom data and updates it (`FD-feed`, `FD-feed-custom`); A adds an activity with free text to its own feed and edits it (`FD-activity`, `FD-update`); A adds an activity to B's feed (`FD-other-feed`); B reads A's feed and queries A's activities (`FD-read`, `FD-query`, no-leak cases); B follows A's feed from its timeline, comments on and reacts to A's activity (`FD-follow`, `FD-comment`, `FD-reaction`). No request rings, notifies, joins, records or broadcasts; every Feeds write carries `skip_push: true`.
- **Fixtures.** The objects a case needs (a call of A's with A and B as members, a call of A's alone, A's and B's feeds, B's timeline, an activity of A's) are created server-side by the case's fixture requests, each sent once per run, through the guard; what they create is recorded as the run's. A fixture Stream does not answer with 2xx leaves the case INCONCLUSIVE, "fixture not in place", without its step.
- **The positive control** is the same request succeeding: the server's replay for a refused request (with the acting user named where a server request needs it), or, for the no-leak cases, the same read by A (its own call or feed) or the server's replay, which must find the data.
- **Verdicts.** Before the lockdown a **FAIL** records a capability: the client's request succeeded, or B read A's custom data, activity or call ID. After the lockdown every case must **HOLD**; a FAIL then is a capability the configuration did not remove, recorded plainly for Nathan's decision, as S15 was. The lockdown empties only the `user`, `guest` and `anonymous` grants (see "The Video and Feeds lockdown"), so what a call's member or a feed's owner may do through the resource roles Stream gives them (`call_member`, `feed_member` and the like) is expected to stay: the fake models a member reading its call and an owner posting in its own feed, and the live run shows what Stream keeps. The disclosure rule applies to the no-leak cases: an ID the request carried (the call in the path, A in the query) is not a disclosure.
- **The product-finding rule** (DM-05 finding 2 (c)). An answer to a case's request, or to its fixture, whose status is 4xx other than 402 and 404, whose Stream code is not 99, and whose message says the product is not enabled or not available to the application (`usage.product_unavailable_wording`: the phrase "not enabled", "not available", "not activated", "is disabled" or "not on the plan", about the product, the feature, the application or the plan, and naming no object or field of the request such as a feed group, a call type, a field or a user; Stream documents no such message, so the words are conservative: Stream's "Not Allowed" and an input error like "feed group 'x' is not available" do not match, and a 404 is an object that does not exist), is that product's finding: the row's verdict is **NOT AVAILABLE (the product is not enabled for the application)** with Stream's message as its reason, the product's remaining cases are "not run" with the same verdict, the run goes on with the other product, and cleanup proceeds. Such an answer is not a charge signal when its only charge word is "upgrade"; wording about a charge, a payment, an overage, billing, a quota or a plan limit still is one, and so are 402 and code 99 (see "Signals, by kind").
- **Undo and cleanup.** A client success is undone where an undo is defined (the call deleted, B removed from the call, the custom data put back, the follow and the reaction removed); when the control's replay succeeded on the same object and made the same undo, the client's success is not undone a second time (`Control.undo_once`: a second delete would get 404 and stop the run for nothing), and the row says so. `FD-feed` has no undo: Stream does not recreate a deleted feed ID (`GetOrCreateFeed failed with error: "feed with id: … has been deleted"`, even after `hard_delete=true`; run V1 of 27 September 2026 left eight Feeds cases INCONCLUSIVE that way), and the later Feeds cases need A's feed, so the replay's feed stays, recorded, and cleanup deletes it. An object with a server-assigned ID (an activity, a comment) is recorded and deleted at cleanup instead. Every call, feed, activity, comment, reaction and follow a fixture, a control or a client creates is recorded from the answer, so the guard owns it and cleanup deletes it.

## Budget guardrails

Per session, the harness counts synthetic users, channels, concurrent connections and API calls, and stops before passing any of them:

| Resource | Limit per session |
|---|---|
| Synthetic users | 20 |
| Channels | 30 |
| Concurrent connections | 10 |
| API calls | 5,000 |

Server calls are counted before they are sent. Client calls are capped per command inside the runner. The count persists in the ignored `.work/usage-ledger.json`, so it covers every run of one checkout; a fresh clone starts at zero.

A response that suggests a charge, an upgrade or an exceeded limit stops the run at once: HTTP 402 or 429, Stream code 9 or 99, or wording about billing, quotas or upgrades. The check covers every server response, including the typed SDK calls such as `upsert_users` and `send_message` (P06.1-C1), and every client request: a command's own; one the SDK sends between commands, and one answered only after its command replied, both of which the runner reports in the next reply, or in its exit reply as the session closes; and every asynchronous SDK error, with Stream's status and code when it carries them (P06.1-I2a; the C3 review's gap: until then such requests were neither checked nor recorded, and an asynchronous error was only noted). A request the runner refused before sending it is not a signal. Calls the SDK sends between commands are counted like any client call; one found only as a session closes is counted without a check that could stop the run there, so the next reservation stops it if the budget is passed. A signal found as a session closes is recorded, and raised only when no other exception is in flight; at the end of the run it is never raised, and the cleanup is decided after the sessions close. The run records every such signal wherever it meets it (P06.1-C3): the server client and every client session record it in the run's usage ledger as they raise its stop, so no later exception can lose it. That covers a signal met as the run's own stop; behind another stop that stays the run's stop (for example a budget stop in flight when a restore meets a charge signal, or a key still overridden when B's probe meets one); replaced in flight (a Ctrl-C, or an error, while a case's `finally` closes a client session); in a restore at the end of the run; in the cleanup; or in the final configuration read. If an error after which the run would go on replaced the stop, the run stops once that case's row is recorded. After any of them the run deletes none of its users or channels ("cleanup skipped: …"), sends no undo of a client success and no unset of A's member field in S15, but it still restores any temporary change in its journal and re-reads the configuration. A restore left undone would leave the application less locked down than recorded. Once the signal is understood, `cleanup --apply` deletes the run's data. (Changed in P06.1-C3: until then only the run's own stop was checked, and only by its message, so a signal met by the end of the run, behind another stop or replaced in flight did not stop the cleanup, and S15 still sent its unset.)

The calls this costs (corrected in P06.1-C2: the README said "at most two or three calls per journalled change"). One restore attempt is at most three calls: the restoring `PUT` or `PATCH`, a re-read and, for AB's `read-channel-members` grant, B's members query. A journalled change gets one attempt when its case ends and, if that fails, one at the end of the run. The end of the run tries twice more, 10 s and 20 s apart, only when that attempt's own failure was a rate limit (HTTP 429 or Stream code 9) or not a stop signal (a 5xx, or a re-read that still shows the change). So a journalled change costs at most six calls when its restores are refused with a charge signal or stopped by the budget, and at most twelve otherwise. Then two reads of the configuration.

The matrix stops early enough to keep 190 API calls for the end of the run (130 until P06.1-I2b), plus 30 for the case in progress, or the number of calls a P06.1-I2a case declares it can use (up to 120 for a mechanism family) (P06.1-I2a). The measured worst case for the end of the run, with every delete task polled 30 times, a journalled restore failing all three attempts and one Video or Feeds object of every kind to delete (P06.1-I2b), is 172 calls (`tests/test_cleanup.py`).

**The run plan** (P06.1-I2a; DM-04 finding 5). Before any live call, `checks/run_plan.py` runs the complete set (the I1 matrix and every I2a case) against the fakes, whose reservations go through the same usage ledger a live run uses, and then each case family (a group of the matrix) alone after the base setup, as a rerun would. Run 1 may use the complete set's count only if what is left still covers one rerun: the base setup plus the largest single case family. The count at this head: the complete set uses 11 synthetic users, 18 channels and a peak of 6 connections; the largest rerun needs 7 users (revocation, or suspension and deletion), 8 channels (creating and joining) and 5 connections; so 18 of 20 users and 26 of 30 channels. A case that fails in a way that creates data can reserve more: `EO-channel` one channel, if a probe created the missing one. The caps are per session, so the plan adds what this checkout's usage ledger (`.work/usage-ledger.json`, read only) says earlier live commands used (`session_used_before`; the independent review, a nit); the same numbers, with the ledger's, decide whether a rerun fits.

**P06.1-I2b's plan** (its prompt, section 5; DM-05 findings 2 and 6). The same script also counts run 1, the chat reruns only (`matrix.RUN_1_CASES`: RV-remove, SD-deactivate, F9-thread, F9-sync, EO-channel, EO-user, EO-message and S3a), run V1 and run V2 (the Video and Feeds cases, with the lean setup) and the largest of the three in reserve; the plan fits only if the four together, with the ledger's count, fit the caps (`i2b_fits`). At this head: run 1 uses 7 users and 4 channels (the base setup, M1, M2 and S, and their channels), run V1 and run V2 2 users and no channel each, with a peak of 4 and 2 connections; with run 1 in reserve, 18 of 20 users and 8 of 30 channels. `python checks/run_plan.py --only <case ids>` prints one set's own count. The complete set now holds 132 cases (114 at I2a and the 18 product cases) and still fits with the largest family in reserve.

**Signals, by kind** (P06.1-I2a; DM-04 finding 4). The harness stops the same way for every charge or limit signal: at once, deleting nothing. What the operator does next depends on the kind, and the problem "cleanup skipped: …" says which:

- **A charge signal:** HTTP 402, Stream code 99, or wording about billing, payment, an upgrade, an overage, a charge, a quota or a plan limit, including a rate limit whose wording says so. Make no further live call, and report it.
- **Only a rate limit:** HTTP 429 or Stream code 9, without such wording. Wait at least the rate-limit window (60 s, or the reset the answer gave: a server stop's message names `x-ratelimit-reset`, and a client's rate-limited request keeps its own `x-ratelimit-*` headers and no other header), then run `cleanup --apply` once, `verify-clean` and `configure` (a dry run). The reserve rerun stays available if those pass. A second rate limit ends live work.
- **A `deleted-user-1729640-…` user left after `cleanup --apply`** is reported and left (the I2a prompt). The run's preflight counts it as a user the proof did not create, so no further run can start: the reserve rerun is then not available, and live work ends (the independent review, point 9).
- **A product-availability answer is a finding, not a charge** (P06.1-I2b; DM-05 finding 2 (c)): a refusal whose status is 4xx other than 402, whose code is not 99, and whose message says the product is not enabled or not available to the application is recorded as that product's finding (see "P06.1-I2b cases"). It ends that product's cases, and cleanup proceeds, because cleanup deletes only the run's own data through the guard, so nothing it sends can incur a charge. A `_CHARGE_WORDS` match on "upgrade" alone in such an answer is not a charge signal; wording about a charge, a payment, an overage or billing still is, and 402 and code 99 always are.

## The guard (P06.1-I2a)

Every server request passes one guard before it is counted or sent (`glow_stream_proof/guard.py`; DM-04 finding 1). The server client calls it from its request hook, so the SDK's typed calls pass it too, and a refused request never leaves the process. During `run` the run itself is the guard's scope; a refusal stops the run like any stop condition (`stopped: guard refused …`, exit 2), after the case's row is recorded. The guard refuses:

- a request that bans, deactivates, deletes, revokes tokens, hides, freezes, removes a member, or updates a user or member, when a user or channel it names is not the run's: neither one the run recorded nor one whose ID contains the run's prefix. A member named in the path (`channels/{type}/{id}/member/{user_id}`) counts too (P06.1-I2a, step 2);
- any `PATCH /api/v2/app` other than a journalled temporary setting (only guest user creation, for G1's control), so an application-wide token revocation is refused;
- a channel-type change other than a journalled `glow-match` toggle, with the fixed settings at their production values;
- any change to a message the run did not record (an edit or partial update, an action, a reaction and its removal, an undelete, a delete, a vote on its poll: every mutating `messages/{id}` path; P06.1-I2b, the I2a review's nit 4: until then only the delete checked the message), or a change to a poll or user group the run did not record; a poll update that names its poll in the body (`PUT /api/v2/polls`) counts too, and so does a mute's `target_id` among the users a request names (P06.1-I2a; the independent review, a nit). The run records every message it creates, S10's poll message included, so the server replays that are the controls of S3a, S3b, S4a, S4b, S5 and S8, and S10's server vote, pass;
- any other kind of change the proof does not make, for example a batch channel update, a retention policy or a role;
- **in Video and Feeds** (P06.1-I2b; DM-05 finding 3): first, anything on the deny-list, whatever it names: a path holding `join`, `go_live`, `start_`, `stop_`, `broadcast`, `recording`, `transcription`, `caption`, `ring`, `notify`, `rtmp`, `hls` or `egress`, or a body or query carrying `ring` or `notify` (any value), `video: true` or `create_notification_activity: true` (each key in any letter case, and `true` as a boolean or as `"true"` in any letter case, since P06.1-C4) (a media session, a push, a recording or a broadcast: each could reach a device or incur a charge); then a Video or Feeds configuration write (a `PUT` of one call type's or one feed visibility's grants), which passes only in the scoped `configure`'s own scope (`guard.ConfigureScope`) and only with the lockdown's body (`grants` alone, naming client roles only, each `[]`), never during a run, and a call type's creation or deletion or a feed group change, which pass nowhere; then any request outside the families the runner's `product` op allows (`client/product-op.cjs` and `glow_stream_proof/products.py` hold the same table, and a test checks that they agree): a call's creation, update, members, custom event and delete on a call the run created; a feed's creation, update and delete, an activity, a comment, a reaction, a follow and their deletes on feeds and activities the run created or recorded; and a run user's Feeds data delete. Every user such a request names must be the run's. The queries (`POST /api/v2/video/calls`, `/api/v2/video/call/members`, `/api/v2/feeds/feeds/query`, `/api/v2/feeds/activities/query`, `/api/v2/feeds/comments/query`, `/api/v2/feeds/follows/query`) are reads.

Reads, including the POST queries the proof makes, are never refused. A refusal names the request's shape and its reason, never an identifier. `cleanup --apply` is guarded by the proof's prefix alone: it can delete only users, channels, calls and feeds whose IDs contain `p061i1-`, and the Feeds data of such users. `configure --apply` and `restore --apply` are operator commands outside the guard; `configure --products video,feeds --apply` runs inside the guard's configure scope, which allows nothing but the two configuration writes.

**The runner's `product` op** (P06.1-I2b) is how a case sends a Video or Feeds request as a modified client would, with the session's own token: a method, a path and a body, through the chat SDK's own request path (`client.post(url, body)` and its kin), so Stream's `api_key`, `user_id` and `Authorization` are attached as for any chat request. Before anything is sent the op refuses, in code, the same deny-list and anything outside the allowlist (kind `refused` in the reply; it is never a signal), and the command's call cap applies. The host is the chat host Stream's server SDK uses for every product; a case may name Stream's documented Video or Feeds host instead (`host: video|feeds`), and no other. Nothing here sends a delete or a configuration write.

**Nothing else reaches Video or Feeds** (P06.1-C4; the I2b review's finding 1: until then the generic `call` op could send a client `post` to a product path, and only the budget stopped it). The runner's request interceptor applies the product op's own check (`productRefusal`) to every request, whatever op made it, whose host is the Video or the Feeds host, or whose path lies under `/api/v2/video`, `/api/v2/feeds`, `/video` or `/feeds` (the Video and Feeds clients' own bare forms) once letter case, percent-encoding and dot and empty segments are normalized. Percent-encoding is decoded byte by byte, round after round, so an escape that is not valid UTF-8 (`%ff`, `%c0`) or not hex (`%zz`) never stops the decoding; a path whose encoding still changes after eight rounds is refused, on any host (C4's own review found that `decodeURIComponent` threw on `%ff` and left a `%76ideo` path unseen; the blocking finding of that review). The runner sends nothing but `https:`, to no host but Stream's chat, Video and Feeds hosts, nothing with a `Host` or forwarding header (`X-Forwarded-Host`, `Forwarded`, `X-Original-Host`, `X-Host`) of its own, nothing with a request-rewriting header (`X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override`, `X-Original-URL`, `X-Rewrite-URL`; P06.1-C5, the manager's addition to the C4 review's finding 1), each header name read trimmed and in any letter case, as axios sends it (P06.1-C5: until then a name padded with whitespace, such as `" Host"`, passed the check and axios sent it trimmed), and with an underscore read as a hyphen, as some servers read it (C5's own review: `X_HTTP_Method_Override` passed the check), and follows no redirect (`maxRedirects: 0` on every request), so no request can reach another host or another virtual host unchecked (C4's own review). The URL is resolved as axios will send it (its `buildFullPath` against `config.baseURL`, then `new URL`). The check sees the method, the path as sent, the body and the query (the URL's own and `params`, and any query value that parses as JSON, as Stream's `payload` does). A product path whose form as sent is not its normalized form is refused outright, and so is a product request whose body the check cannot read (a string that is not JSON, which axios would send form-encoded, a form, a buffer or a stream; found by C4 in its own reading); letter case is folded to find a product path but kept in that comparison, because an ID may hold capitals, and the allowlist's fixed segments are lower case, so a miscased fixed segment is refused by the op's check. The check runs before the budget: a refused request is neither counted nor sent nor recorded, and the reply's error kind is `refused`, as for the product op. The 18 product cases' requests pass it unchanged (`tests/test_runner.py`, `ProductReachTest`). `matrix.validate` also refuses a case step that could reach a product through any op but `product`: a `call` of one of the client's methods that take the request's URL (`get`, `post`, `put`, `patch`, `delete`, `sendFile`, `doAxiosRequest`, `setBaseURL`), or a `get` of a product path. No case did either. Since P06.1-C5 (the C4 review's finding 1) it refuses every `call` step outside an explicit allowlist (`matrix.CALL_ALLOWLIST`): each target and method the matrix uses, with the most positional arguments any of its steps passes, so no step reaches a request-options argument, and never the client's reminder methods, which put a caller value into the path unencoded (see "Limits", "Added in P06.1-C4", request options). A `call` step whose method is not a name, or whose arguments are not a list, is refused too (C5's own review: the runner looks a method up by its string form, so `["createReminder"]` would have reached the reminder method, and `validate` raised on it instead of refusing it). The deny-list matches a denied key in any letter case, and a denied-true key's value as a boolean `true` or as `"true"` in any letter case, in both tables (P06.1-C4; the I2b review's nit 3).

## What a run and `configure --apply` change, and how to restore

`configure --apply` sets:

- `disable_auth_checks=false` and `disable_permissions_checks=false`. Both were already false.
- `guest_user_creation_disabled=true`. It was false.
- Empty `.app` grants for `user`, `guest` and `anonymous`. `user` had 24 grants, including `search-user`, `update-user-owner` and `create-user-group`. `guest` had 4.
- Empty grants for every role in the five default channel types. Their features are unchanged.
- The `glow-match` channel type: members get `read-channel` only, every other role gets nothing, and every content feature is off, including typing events. Read events stay on.

The configuration stays in place for P06.1-I2.

The configuration check (`configuration.verify`), which preflight, the end of every run and the dry-run `configure` use, also compares every application setting the committed baseline records with its recorded value, except guest creation, which the lockdown changes on purpose (P06.1-I2a; DM-04 finding 2). So an application-wide `revoke_tokens_issued_before`, a webhook, an event hook, a custom action handler or a changed upload or moderation setting shows as a difference. A setting the baseline does not record was absent from the application then (for example `before_message_send_hook_url`), and must still be absent or empty.

During `run`, some cases change settings for a few seconds (corrected in P06.1-C1: at I1's head only the type features and guest creation were re-read after their restore, channel-override removals were never re-read, and a failed restore did not stop the run):

- the `config_overrides` of channel AB (replies, reactions, uploads, a `read-channel-members` grant);
- `glow-match` custom events and polls;
- guest creation, for the guest control, and for G2's server-created guest if Stream refuses to create it while creation is disabled (P06.1-I2a);
- `glow-match` custom events for `F9-ai`'s permission-layer phase (P06.1-I2a).

The P06.1-I2a mechanisms change no setting: they act only on the run's own users and channels, through the guard, and cleanup deletes what they leave.

Each change is written to the run's journal before its enabling request is sent. When its case ends, however it ends, the change is restored and verified:

- the type's features and the app's guest setting are re-read and must show the production values;
- AB is re-read while its override is set, and again after the removal. A re-read proves the removal of a key only if it showed that key as overridden while it was set; the key must then read clear. If the re-read did not show the `read-channel-members` grant, B's members query must be refused again. Any other key the re-read cannot show is recorded as **not verified** (the removal request was accepted), and the run exits non-zero at its end. The re-reads' shape (key names only, no values) is kept in the case's detail, because Stream's response shape for this read has not yet been seen live.

A restore that fails, or that reads back wrong, stops the run. If a guardrail stop was already in flight, both are recorded and the guardrail stays the run's stop; if the restore itself met a charge or limit signal, that signal is recorded as well, so the end of the run deletes nothing even when the guardrail in flight was only the budget (P06.1-C3). Anything still in the journal is restored at the end of the run, after a timeout or Ctrl-C too. A removal of AB's override that Stream accepted, but that could not be verified (for example, B's members query was stopped by a guardrail, while no key still reads as overridden), is not "not restored": it leaves the journal, is recorded as not verified, and the run exits non-zero (P06.1-C2).

The undo requests that reverse a control's change (message text, roles, memberships, channel data, uploads, A's member field) are checked too. A failed undo stops the run once its case is recorded. So does a failed restore of A's role in E5, when the role reached Stream's stored state (P06.1-C2: until then an exception there was recorded as a harness error and the run went on with A holding the role), and so does a read of A's stored user in E5 or S14 that fails (P06.1-C3). The undo of a client success follows "A client success that must be undone" under "Verdict rules".

If B's members query, the probe that checks a grant's removal, meets a guardrail while another key of the same override still reads as overridden, the run stops on the override (the change stays journalled), and B's probe stop is kept in the stops, its signal recorded (P06.1-C3; until then it was dropped). Every override today has one key.

The run's own users, channels, polls and user groups are deleted.

To restore the recorded baseline, check the plan first, then apply it:

```bash
.venv/bin/python -m glow_stream_proof restore                            # plan only
.venv/bin/python -m glow_stream_proof restore --apply                    # grants and guest setting
.venv/bin/python -m glow_stream_proof restore --apply --delete-match-type
```

`--delete-match-type` works only when no `glow-match` channel exists. Stream's documented alternative is to send `grants: null` for a scope, which resets it to Stream's defaults. The live grants were not checked against Stream's defaults.

Side effect: the admin role's grants in the default types and in `glow-match` are empty too. A dashboard tool that acts client-side as the dashboard user may therefore be refused in those types until restored. This is unverified.

### The Video and Feeds lockdown (P06.1-I2b)

The general `configure --apply` above is not a difference: it re-sends the application `PATCH`, the five default types and `glow-match` every time. It is the operator command that reapplies the full chat target, outside the guard, and P06.1-I2b never runs it (DM-05 finding 1). The one lasting change of P06.1-I2b is the scoped, differential command:

- `configure --products video,feeds` reads the chat configuration and both products' (the call types and their grants, `GET /api/v2/video/calltypes`; the feed visibilities and their grants, `GET /api/v2/feeds/feed_visibilities`; the feed groups, `GET /api/v2/feeds/feed_groups`), prints the chat verification ("differences before"), each product's availability, the products' differences from their target, and the plan. The plan is a difference: one `PUT /api/v2/video/calltypes/{name}` or `PUT /api/v2/feeds/feed_visibilities/{name}` per call type or feed visibility where `user`, `guest` or `anonymous` still holds a grant, naming only those roles with `[]`. Stream documents that a grants update changes only the roles named, so `admin` and the resource roles (`call_member`, `feed_member`, …) are untouched. Nothing is planned for a scope that already reads as the target, nor for a product that is not available. `--products video` or `--products feeds` plans one product.
- `--apply` refuses, in code, while the chat configuration does not verify (the chat differences alone: once the lockdown is recorded as applied, the products' own drift is what a re-apply is for), and if any planned request is not one of the two configuration writes; it names only `video` and `feeds`. It sends the plan inside the guard's configure scope, which allows nothing else, re-reads chat and both products, and prints "differences after", which must be `[]`. The record (`.work/configure-products-<stamp>.json`) keeps the full before- and after-state in `products.baseline_record`'s shape, every role's grants and every call type's settings, feed visibility and feed group, scanned like every other record (P06.1-C4; the I2b review's finding 2: until then it kept the client roles' grants only). A `PUT` that fails mid-plan still leaves the record, with the steps applied so far, the failure and the re-read after-state, and the command exits 1. After a charge or limit signal nothing more is sent: the ledger refuses no later request by itself, so the command reads the ledger's recorded signals, skips the re-read, writes the record with `after: "after-state not read: a charge or limit signal was met"` and exits through the guardrail stop (exit 3); a Ctrl-C also skips the re-read. The ledger, not the exception's type, also decides what reaches `main`: after a signal, the signal's stop does, even when an ordinary error replaced it in flight, with that error chained to it; only a Ctrl-C is kept instead (P06.1-C5, C5's own review: until then that error reached `main` and the command exited 1). If the record's own write then raises (the leak check refuses the record, or the disk write fails), the stop still reaches `main` (exit 3) with the write's error chained to it, and a printed line names the write's error, the signal, and what ended the apply when that is neither the signal nor a refused step (P06.1-C5; the C4 review's nit 4: until then the write's error replaced the stop, and the command exited 1 without naming the signal). The general `configure --apply` does the same (P06.1-C4; the I2b review's nit 8, with the manager's addition).
- **Why it is narrower than I1's lockdown** (DM-05 finding 9 (a)): I1 emptied every role's grants in the chat types, `admin` included (OD-13's side effect). Glow's tokens carry the `user` role, so this lockdown removes only what `user`, `guest` and `anonymous` tokens can do, and spares the dashboard user's Video and Feeds. What a call's member or a feed's owner can do through a resource role is therefore not removed, and the run after the lockdown (run V2) records it.
- **Verification.** `configuration.verify` compares the products with the target too, so preflight, the end of every run and the dry-run `configure` see any drift. Since P06.1-C4 the target is more than the client roles (the I2b review's finding 2): `user`, `guest` and `anonymous` must hold no grant (absent or `[]`), and everything else the committed products baseline (`baseline/video-feeds-1729640-2026-09-27.json`) records must be as it records it: every other role's grants in every call type and feed visibility (compared as sets), each call type's `settings` and `notification_settings` (field by field, value and type), and each feed group's `default_visibility` and `default_follower_role`; a call type, feed visibility, feed group or role present on one side only is a difference. `availability` has its own rule (below) and the read answers (`read`, `feed_groups_read`) describe the read, not the configuration; no field the record keeps is a timestamp or otherwise volatile. The offline fake products model the same baseline, so the runs, preflight and the dry-run `configure` verify offline with no difference. The comparison has not been used live: the re-read after the apply of 27 September compared the client roles only. It applies from the commit that records the live apply on (`products.LOCKDOWN_APPLIED`, set to 2026-09-27T05:58:31Z, the apply's UTC stamp; `None` until then): before the apply the products' differences are the plan, not drift, and the runs before the lockdown (run 1 and run V1) must be allowed. A product whose configuration read is not 2xx is never locked and never a difference when it is not available; a read that is not verified (a 5xx, an outage) is a difference, because the state is not known.
- **The baseline and restoring.** `baseline` reads the products' configuration into its snapshot (settings and grants; no user, no data), and `record-products-baseline --snapshot <file>` writes `baseline/video-feeds-1729640-<date>.json` from it, committed before the apply. `restore` does not touch the products: to return them, send each recorded scope's grants back with the same `PUT`s (the plan in reverse), which no command does; the committed chat baseline is unchanged.

## Limits (added in P06.1-C1)

- The client processes are isolated by their environment only: they run as the same operating-system user as the server process, with the secret kept out of their environment by an allowlist and the runner's refusal.
- `verify-clean` cannot see soft-deleted channels. C13's control soft-deletes AB before cleanup; cleanup hard-deletes every channel the run recorded, by ID, and requires the delete task to report `completed`.
- Charge detection reads HTTP statuses, Stream codes and error wording. It cannot see a charge Stream does not signal in a response.
- The client endpoints listed in the I1 review's finding 9 were never tried, and G2 and S10 needed new setups (P06.1-I2a adds them).
- The poll and user-group listings (`POST /api/v2/polls/query`, `GET /api/v2/usergroups`, paths from `getstream` 6.1.0) and the channel re-read used to verify override removals (`POST /api/v2/chat/channels` filtered by `cid`) had not been run live before P06.1-I2a. A listing Stream does not answer with 2xx is reported as not verified, with Stream's message, and so is an override removal the re-read cannot show; either makes the run exit non-zero. The poll listing's first live use (`verify-clean`, 26 September 2026) got HTTP 400 code 4: Stream's server-side Query Polls needs a user, and the proof never uses the dashboard user. Since P06.1-I2b a run's cleanup lists polls as each of its own users (`POST /api/v2/polls/query?user_id=…`, a deactivated user left out) before those users are deleted, and reads each recorded poll by ID after its delete (`GET /api/v2/polls/{id}`), which must answer 404. Whether a listing as a user shows that user's polls or every poll it may see is not documented; under preflight's guarantee that the application holds no other user, every poll of the run was created by, or on behalf of, one of its users, so an empty union of the listings shows that none remains, and it stands in for the standalone listing in the run's verify-clean (`remaining_polls`). A listing Stream refuses leaves the polls "not verified", with Stream's message, and a recorded poll that still answers after its delete is a problem; either makes the run exit 4. The standalone `verify-clean` command has no run user to list as, so its poll listing stays "not verified" (exit 1); it says so.
- The standalone `verify-clean` command has no preflight to compare with, so it reports every poll and user group present.
